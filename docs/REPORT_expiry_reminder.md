### Что считает `findExpiringSubscriptions(days)`

Подписки (с `JOIN users` по `user_id`, строки без пользователя пропускаются), у которых одновременно:
`status IN ('trial','active')`, `started_at <= NOW()` (уже идёт, будущие периоды очереди не берутся),
`expires_at > NOW()`, `expires_at <= NOW() + INTERVAL '1 day' * days` и `expiry_reminder_sent_at IS NULL`. Возвращает
`id, user_id, plan, status, started_at, expires_at, email`, по возрастанию `expires_at`. Число дней приходит
параметром из `EXPIRY_REMINDER_DAYS`; другой тройки, привязанной к напоминанию, в `src` и `server` нет (поиск:
константа объявлена в `tariffs.js`, используется в `server.js` только как импорт и один вызов).

### Порядок в `runExpiryReminders`

Выход при `!dbReady` или если прошлый прогон ещё идёт. Затем выборка → для каждой подписки (в своём `try/catch`):
очередь `getSubscriptionQueue(user_id)` → правило пропуска → `claimReminder(id)` (при `false` — пропуск) →
`sendRawEmail` → при `false` или исключении `releaseReminder(id)`. Письмо не может уйти без отметки: отправка
стоит строго после успешного захвата. Побочное следствие: если процесс упадёт между захватом и отправкой, письмо по
этому периоду не уйдёт вовсе (отметка стоит); это сознательный выбор «лучше без письма, чем дубль».
Лог — одна строка на прогон и только если что-то найдено: «найдено / пропущено (продолжение оплачено) / отправлено /
не удалось»; адреса не пишутся, ошибки по подписке логируются по её id.

### Правило пропуска (2.4)

`isContinuationPaid(sub, queue)`: в очереди есть период со строго более поздним `expires_at`, чем у текущей
подписки, и уровнем (`club = 1`, `pro = 2`, через `tierOf`) не ниже. Строки очереди не содержат `id`, поэтому
«другой период» определяется по более позднему `expires_at`. При пропуске отметка не ставится — письмо уйдёт на
следующем прогоне, если очередь изменится.

### Таймер

В `start()` после `app.listen`, только при `dbReady`: `setTimeout(runExpiryReminders, 2 мин)` и
`setInterval(runExpiryReminders, 60 мин)`. Новых зависимостей нет.

### Письмо

Тема «Подписка РПКМ заканчивается {дата без года}» и тело — по утверждённому тексту; дата по Москве, с годом и
неразрывным пробелом перед «г.» (как в ТЗ, `.replace(/\s+г\.$/, ' г.')`; «г.» входит в форматируемую дату,
второй точки нет); название плана через `escapeHtml(labelOf(plan))`; ссылка на `${SITE_URL}/pro` или `/club`
(кликабельная), стили в духе письма с кодом входа. Ничего рекламного не добавлено. Формулировка «на странице {Клуба
/ PRO}» взята из тела письма: «на странице Клуба» / «на странице PRO» (в списке подстановок ТЗ стоит «страницы PRO» —
расхождение в падеже, выбран вариант тела).

## Проверка

- `node --check server.js` и `node --check server/db.js` (по отдельности) — ОК; `npx vite build` — без ошибок.
- Код оркестрации (`isContinuationPaid`, `buildExpiryReminderEmail`, `runExpiryReminders`) взят из `server.js` как
  есть и прогнан узлом с заглушками БД и отправки (реальной БД и почты нет):

| Сценарий | Результат |
|---|---|
| 1. Платная (Клуб · месяц) без очереди | захват → отправка, без снятия; в логе нет `@`, счётчики верны |
| 2. PRO-триал, в очереди PRO на месяц | письма нет, отметка не ставится, учтено как «пропущено» |
| 3. PRO заканчивается, в очереди только Клуб | письмо уходит, ссылка `…/pro`, «на странице PRO» |
| 4. Клуб, в очереди PRO | пропуск (уровень выше) |
| 5. Отправка вернула `false` | отметка снята; следующий прогон отправляет, отметка остаётся |
| 6. Повторный прогон после успеха | второго письма нет (отметка) |
| 7. Исключение в отправке у одной подписки | отметка снята, остальные письма идут |
| 8. Два прогона одновременно | ровно одна отправка (флаг «прогон идёт») |

Также выведен текст письма (тема «Подписка РПКМ заканчивается 10 октября», тело по ТЗ).
