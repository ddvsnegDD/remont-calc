## Что сделано по частям

### Часть 1 — схема и удаление пользователя (`4aa3f50`)

Четыре новые таблицы (`calculations`, `checklists`, `checklist_photos`, `consultations`) через `CREATE TABLE IF NOT EXISTS`, типы и имена колонок как в ТЗ буквально. Все четыре — `user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE` (проверено `grep -n "REFERENCES users(id)" server/db.js` перед этим отчётом — совпадает с ожиданием, `subscriptions.user_id` осталась без `ON DELETE`, как и просило ТЗ).

`deleteUser` переписан в одну транзакцию (`pool.connect()`/`BEGIN`/`DELETE subscriptions`/`DELETE auth_codes`/`DELETE users ... RETURNING *`/`COMMIT`, `ROLLBACK` в `catch`, `release` в `finally`). Вызов `deleteUserFiles` в эту часть не вошёл осознанно — модуль `server/storage.js` появляется только в части 2; при выполнении части 1 это было явно сказано в чате и оставлен код-комментарий, довёл в части 2.

### Часть 2 — файловый слой (`03a978b`)

`server/storage.js`: `UPLOAD_DIR` из окружения (не в коде), при незаданном — предупреждение в лог, эндпоинты загрузки отвечают `503`; раскладка `UPLOAD_DIR/<user_id>/<uuid>.jpg`; `photoPath` резолвит путь и сравнивает с `UPLOAD_DIR/<user_id>/` — защита от `../` в имени файла.

`deleteUser` дозаписан: `deleteUserFiles(userId)` вызывается после `COMMIT`, ошибка удаления файлов — в лог, не бросается. По ревью (перед частью 3, тем же коммитом): `userDir` бросает исключение на не-целочисленный/неположительный `userId` (защита от рекурсивного удаления не туда), `deleteUser` зовёт `deleteUserFiles` только если `rows[0]` (пользователь реально был в базе).

Проверено изолированно (Node-скрипты, без БД, до коммита): путь с `../` в имени отклоняется, `deleteUserFiles` без `UPLOAD_DIR` — no-op, имена файлов — `crypto.randomUUID()`, реальный `fs.rm` на временной директории удаляет её рекурсивно.

### Часть 3 — эндпоинты (`29c6c5e`, фикс ревью `622940a`)

Все обработчики берут пользователя через `findUserByEmail(req.user.email)`, не через `req.user.id` из токена (по ТЗ — у удалённого и заново зарегистрированного пользователя токен может жить со старым id).

По пяти замечаниям ревью: `CHECKLISTS`-справочник + `requireValidChecklist` (404 на неизвестный `checklistId`) и проверка формата/существования `itemKey` — до `savePhoto`, не после; сигнатура JPEG (`FF D8 FF`) в дополнение к mimetype (mimetype в `multipart` клиент может выставить произвольно); `X-Content-Type-Options: nosniff` на отдаче фото; удаление файла с диска, если запись в БД после `savePhoto` не создалась (не оставляем осиротевший файл); `parsePositiveIntId` — ранний `404` для нечисловых/нецелых `:id`.

По трём раундам ревью, в порядке:

4. `saveChecklist` с `keepalive` — если тело `PUT` больше 60 КБ (браузерный лимит на суммарный размер keepalive-запросов), `keepalive` снимается, уходит обычный `fetch`.

Добавлена версия чек-листа (`rev`, `BIGINT`, растущее число от клиента — `Date.now()`, не меньше предыдущего+1) — защита от записи устаревшего состояния поверх нового при гонке двух `PUT` одного пользователя. `flushOnHide` (`pagehide`/`visibilitychange`-hidden) и флеш при смене `id` перестали сбрасывать `dirtyRef` вслепую — это лучшая попытка (best-effort), не подтверждённая отправка; при возврате видимости страницы запускается обычная (ожидающая ответа) очередь `trySave()`, которая либо досохранит и покажет ошибку, либо получит от сервера `{ok:true, stale:true}` (если `keepalive`-флеш всё же дошёл) и корректно обнулит `dirtyRef`.

Найден и исправлен баг вне прямого запроса на правку: `pg` отдаёт колонки `BIGINT` (и агрегаты `COUNT(*)`) строкой — `revRef.current + 1` со строкой слева — конкатенация, не арифметика (`'1758...' + 1 = '1758...1'`), `rev` рос на порядок при каждой загрузке чек-листа и вышел бы за диапазон `BIGINT` за ~7 загрузок. При аудите тем же способом найден и исправлен тот же класс бага в `getAdminStats()` — функции, не связанной с этой задачей и существовавшей до неё: шесть `COUNT(*)` возвращались строками без видимого эффекта (значения только отображаются в `AdminPage.jsx`), приведено к числу для консистентности.

## Отклонения от ТЗ, с причинами

1. **Лимит `express.json()` 500kb (часть 3).** ТЗ просило маршрутный парсер с большим лимитом поверх глобального. Проверено прогоном (реальный Express-сервер) до реализации: второй `express.json()` на маршруте не работает — глобальный парсер уже потребил и разобрал тело первым, `req._body` выставлен, второй парсер поток не перечитывает. Маршрутный парсер не подключён; эффективный лимит на всех маршрутах — дефолтные 100kb от глобального парсера (тела чек-листов без base64-фото укладываются с запасом). Факт задокументирован в самом ТЗ (часть 3) — правка внесена по прямому указанию Дмитрия после того, как я доложил находку до реализации.

2. **Версия чек-листа (`rev`).** Не было в исходном тексте ТЗ — добавлено по ходу ревью части 5 как защита от гонки двух `PUT` одного пользователя. Меняет контракт эндпоинта: `PUT /api/checklists/:id` теперь принимает `{state, rev}` вместо `{state}` из части 3 ТЗ; `GET` (список и один) дополнительно отдают `rev`, чтобы клиент мог засеять свой счётчик при загрузке.

3. **Дубль `plural.js`/`pluralize.js`.** При выполнении части 6 завёл новый модуль для склонения, не проверив, есть ли в проекте уже что-то подобное — оказалось, есть (`src/lib/plural.js`, задача `spec_tiers`, часть 8, та же логика под именем функции `plural` вместо `pluralRu`). Исправлено в части 7.

4. **Обещание «можно копить — до 9 консультаций».** Не из ТЗ, найдено при выполнении части 6: маркетинговый текст на `/club` прямо противоречил принятому в этой задаче правилу «3 в календарный месяц, без переноса» («Решения владельца»). Убрано в части 7 по прямому указанию. Других живых упоминаний не нашлось: `grep -rn "копить\|до 9" src/` — пусто. Единственное совпадение по всему репозиторию — `docs/TASK_positioning_cleanup.md:643`, историческая заметка о задаче 2026 года ранее, которая просто *описывает*, что на тот момент на `ClubPage` было такое обещание (как повод для той задачи) — сама заметка ничего не обещает и пользователю не показывается.

5. **`consultationApi.js` — модуль, не названный в тексте ТЗ.** Часть 6 не просила отдельный модуль для консультаций (в отличие от частей 4/5, явно называвших `calcsApi.js`/`checklistsApi.js`). Завёл `src/lib/consultationApi.js` по той же схеме — для консистентности и чтобы `error:'network'` обрабатывался одинаково во всех трёх местах.

6. **`getAdminStats()` — попутный фикс, вне ТЗ.** См. пункт 6 части 5 выше — найден при аудите BIGINT/COUNT, не связан с расчётами/чек-листами, эффекта не имел.

7. **Тексты лимита — через склонение, не буквальная строка «1 расчёт в месяц».** ТЗ (часть 4) просило перевести тексты на «1 расчёт в месяц» из константы. Сделано через `withCount(FREE_B2B_CALCS_PER_MONTH, [...])` — при текущем значении константы (1) даёт ту же строку, но не потребует ручной правки текста, если константа изменится; аналогично явному требованию части 6 про склонение для консультаций.

## Критерий 12 — исправленное описание

Покрыт двумя независимыми механизмами в `ChecklistDetailPage.jsx`:

- **Размонтирование React** (переход на другой маршрут внутри SPA, включая смену чек-листа между `/checklists/:id` без полного размонтирования компонента) — обычный `fetch` без `keepalive`: JS-контекст страницы не разрушается, запрос успевает завершиться в фоне.
- **Реальный уход со страницы** (закрытие вкладки, обновление, переход на другой сайт, сворачивание/переключение приложений на мобильном) — здесь React unmount либо не срабатывает, либо срабатывает слишком поздно. Отдельно навешаны `pagehide` и `visibilitychange` (`document.visibilityState === 'hidden'`), которые шлют `PUT` с `keepalive: true` — такой запрос переживает сам уход со страницы. Если тело больше 60 КБ, `keepalive` снимается (браузерный лимит на суммарный размер keepalive-запросов).

Оба пути вызывают общий `flushOnHide()`, отправляют безусловно (не ждут ответа предыдущего запроса — в отличие от обычной debounced-очереди `trySave`) и **не сбрасывают `dirtyRef`**: это лучшая попытка, а не подтверждённая отправка. Если страница на самом деле не закрылась (переключение на камеру/другое приложение), а вернулась видимой — второй обработчик `visibilitychange` (не `hidden`) запускает обычную очередь `trySave()`: если `keepalive`-флеш не дошёл, она досохранит и покажет ошибку; если дошёл — сервер отклонит повтор по `rev` как устаревший (`{ok:true, stale:true}`, не ошибка), и `dirtyRef` корректно обнулится.

Живой сценарий (реальное закрытие вкладки/сворачивание приложения на телефоне с реальным сервером) не воспроизведён — см. критерий 12 в разделе ниже.

Не выдаю это за проверку — ниже по каждому пункту явно написано, что именно проверено и на что похоже.

**Удаление**

1. *Полное удаление всех строк и папки `UPLOAD_DIR/<user_id>` после удаления аккаунта.*
   **Не проверено живьём.** По коду: `calculations`/`checklists`/`checklist_photos`/`consultations` — все с `ON DELETE CASCADE` на `user_id` (подтверждено `grep` перед этим отчётом), значит `DELETE FROM users WHERE id=$1` внутри транзакции `deleteUser` каскадно стирает все четыре таблицы автоматически. `deleteUserFiles(userId)` вызывается после `COMMIT`, только если пользователь реально был удалён. Полный цикл (создать данные во всех четырёх таблицах → удалить → проверить ноль строк и отсутствие папки) не прогнан — нет БД и `UPLOAD_DIR`.

2. *Тот же email регистрируется заново — всё пусто, триал доступен.*
   **Не проверено живьём.** По коду: `users.id` — `SERIAL`, не переиспользуется; новый пользователь получит новый id, а данных под старым id уже физически нет (см. п. 1). Логика триала (`hasUsedTrial`, `TRIAL_PLANS`) этой задачей не тронута вообще.

**Изоляция**

3. *Два аккаунта по очереди в одном браузере видят только свои данные.*
   **Не проверено живьём.** По коду: каждый новый эндпоинт фильтрует строго по `user_id`, полученному через `findUserByEmail(req.user.email)` (не через `req.user.id` из токена) — тот же приём, что и в существующем коде подписок.

4. *После выхода в той же вкладке результаты не показывают расчёт предыдущего пользователя.*
   **Не проверено живьём в браузере** (залогиниться не на чем). Проверено по коду: `logout` удаляет ровно те четыре ключа `sessionStorage`, что называет ТЗ; каждая из четырёх страниц результата читает свой ключ в `useEffect` на монтировании — после `logout` ключа нет, страница уходит в свою ветку «нет данных».

5. *Запрос чужого расчёта/чек-листа/фото по id → `404`.*
   **Не проверено живьём.** Проверено чтением всех обработчиков с `:id` в `server.js`/`server/db.js`: везде `WHERE user_id = $1 AND id = $2` (или аналог для фото/чек-листов), несовпадение — пустой результат, обработчик возвращает `404`, не `403`, как и требует ТЗ.

**Лимиты**

6. *Бесплатный профи: 1-й расчёт сохраняется и показывается, 2-й — пейволл; прямой повтор `POST` — `403 limit`.*
   **Не проверено живьём** (нужны БД и реальный месяц). По коду: `countB2BCalculationsThisMonth` считает записи `kind='b2b'` с начала текущего календарного месяца по Москве; при `used >= FREE_B2B_CALCS_PER_MONTH` (=1) — `403 {error:'limit'}`; фронт при этом ответе показывает `ProPaywall` вместо результата.

7. *`pro_trial`/`pro_monthly` — лимита нет.*
   **Не проверено живьём.** По коду: лимит-проверка обёрнута в `if (kind === 'b2b' && tier !== 'pro')`; `tierOf('pro_trial')` и `tierOf('pro_monthly')` оба дают `'pro'` (код `tariffs.js` этой задачей не менялся) — ветка не выполняется вовсе.

8. *6-е фото на пункт — кнопка скрыта; прямой запрос — отказ сервера.*
   **Не проверено живьём.** По коду: фронт скрывает кнопку камеры при `photos.length >= MAX_PHOTOS_PER_ITEM`; сервер независимо считает `countChecklistItemPhotos(...)` и отвечает `403 {error:'limit_item'}` при том же условии — проверка не отменяется тем, что показал клиент, как и требовало ТЗ.

9. *4-я консультация в месяце — отказ сервера; очистка браузера лимит не сбрасывает.*
   **Не проверено живьём.** По коду: лимит считает `countConsultationsThisMonth` на сервере до отправки письма; `localStorage` для этого счётчика в проекте больше не читается ни в одном месте (подтверждено `grep` этой сессией) — очистке браузера физически нечего сбросить.

**Перенос**

10. *Чек-лист, заполненный на одном устройстве, открывается с теми же отметками и фото на другом.*
    **Не проверено — нужны два реальных браузера/устройства с рабочим логином и БД.** По коду: состояние (`checklists.state`, JSONB) и фото (диск + `checklist_photos`) хранятся исключительно на сервере, привязаны к `user_id`, не к устройству — начиная с части 5 в коде не осталось ни одного места, которое читало бы или писало это в `localStorage`.

11. *PDF-акт печатается с фото.*
    **Не проверено живьём** (нужны реальный чек-лист с загруженными фото, логин, попытка печати в браузере). Реализовано и прочитано по коду: `openReportWindow` скачивает фото по id через авторизованный `fetch`, переводит в data URL, только потом вызывает неизменённый `generateReportHTML`; при сбое загрузки хотя бы одного фото — акт не формируется, показывается ошибка. Сам путь «сбой сети при скачивании фото» не воспроизведён вживую.

12. *Отметки и фото сохраняются при быстром уходе со страницы сразу после изменения.*
    **Не проверено живьём.** См. раздел «Критерий 12» выше — оба механизма реализованы и прослежены по коду и жизненному циклу React-эффектов, но ни закрытие настоящей вкладки, ни переключение приложения на телефоне против настоящего сервера не воспроизводились.

13. *Истечение подписки закрывает чек-листы, возврат — восстанавливает нетронутыми.*
    **Не проверено — нужны БД и реальный жизненный цикл подписки.** По коду: `requireChecklistsAccess` на каждый запрос проверяет `tierOf(sub?.plan)` и отвечает `403`, если не `club`/`pro`, но никогда не удаляет строки `checklists`/`checklist_photos` — это то же поведение, что уже было закреплено `TASK_checklists_gate.md` (критерий 7 того ТЗ), эту логику в этой задаче не трогал.

14. *Офисный расчёт открывается из кабинета.*
    **Не проверено живьём.** По коду: кнопка «Открыть» в `B2BCabinetPage.jsx` теперь пишет в `rpkm-b2b-office-current` для `kind==='office'` и в `rpkm-b2b-current` для остальных перед переходом — это и было «баг 6», исправленный в части 4 и подтверждённый на тот момент чтением диффа.

**Уборка и сборка**

15. *После первого захода в `localStorage` нет старых ключей.*
    **Проверено частично, не живьём в браузере.** `grep -rn "rpkm-b2b-calcs\|rpkm_checklist_\|rpkm_consult_" src/` находит эти строки только внутри самой уборочной функции в `main.jsx` — то есть код, который должен это делать, есть, запускается безусловно при загрузке модуля (до рендера React) и не зависит от логина. Не проверено: реально открыть сайт в браузере с заранее выставленными старыми ключами и увидеть, что они исчезли после загрузки.

16. **Числа лимитов только в `src/data/tariffs.js`.**
    **Проверено, живой факт.** `grep -rln` на все четыре константы (`FREE_B2B_CALCS_PER_MONTH`, `FREE_CONSULTATIONS_PER_MONTH`, `MAX_PHOTOS_PER_ITEM`, `MAX_PHOTOS_TOTAL_MB`) показывает только `tariffs.js` и их непосредственных потребителей; отдельный поиск литералов «50 МБ»/«5 фото» вне `tariffs.js` — пусто.

17. **`node --check` для трёх серверных файлов; `npx vite build` проходит.**
    **Проверено, живой факт**, прогнано непосредственно перед этим отчётом:
    ```
    node --check server.js       → OK
    node --check server/db.js    → OK
    node --check server/storage.js → OK
    ```

## Деплой (не выполнялся — для Дмитрия, по ТЗ)

1. **Бэкап базы до `git pull`.** Новые таблицы создаст `initDB()` сама при старте, но без свежего бэкапа откат при проблеме будет некуда.
2. **`UPLOAD_DIR`** — создать на сервере, владелец `deploy`, вне `/home/deploy/rpkm` (чтобы `git pull` его не касался), прописать в `.env`. Без переменной `isStorageReady()` возвращает `false`: сервер при старте пишет предупреждение в лог, а все эндпоинты загрузки/выдачи фото отвечают `503` — само приложение при этом не падает, просто фотофункции чек-листов недоступны до тех пор, пока переменная не появится.
3. **`npm install` после `git pull` — обязательно.** Появилась новая зависимость `multer` (`package.json`/`package-lock.json` уже в git), а обычная команда деплоя, судя по прошлым отчётам, делает только `npm run build`.
4. Сборка и `pm2 restart rpkm` как обычно.
5. **Бэкап `UPLOAD_DIR` — решить отдельно.** Сейчас бэкапится только база; фото на диске бэкап-стратегией не покрыты вовсе.
6. Вне кода (по ТЗ, решает Дмитрий отдельно): на сервере начнут храниться адреса объектов и фото помещений — сверить политику конфиденциальности и, при необходимости, уведомление РКН (запись 77-26-556640).

## Рекомендация перед тем, как считать задачу закрытой

Прогнать на стейджинге или сразу после деплоя, в первую очередь — критерии 1–2 (удаление аккаунта + повторная регистрация) и 10–13 (перенос между устройствами, PDF-акт, быстрый уход со страницы, истечение/возврат подписки): это единственные пункты, где ошибка означает молчаливую потерю пользовательских данных, а не просто неправильный экран. Критерии 6–9 (лимиты) стоит прогнать вторыми — там ошибка означает либо утечку доступа к платной функции, либо ложный отказ настоящему пользователю.
