# Отчёт: /club и /pro показывают очередь оплаченных периодов (TASK_queue_ui.md)

## Часть 1. Сервер отдаёт очередь

**Коммит:** `961dc54` (без push).

### Что изменено

- [`server/db.js`](../server/db.js): новая `getSubscriptionQueue(userId)` — запрос ровно по ТЗ:
  `status IN ('trial','active') AND expires_at > NOW() ORDER BY started_at ASC, id ASC`; возвращает
  текущую подписку и будущие.
- [`server.js`](../server.js): helper `formatQueue(rows)` → `[{ plan, status, tier, startedAt,
  expiresAt }]` (`tier` через `tierOf`); поле `queue` добавлено в ответы `/api/auth/me`,
  `/api/subscription/status` и `/api/auth/verify`.
- Поля `subscription` и `hasAccess` не менялись, `getActiveSubscription`, выдача и возвраты не
  тронуты — доступ по-прежнему определяет только текущая подписка.

### Проверка

- `node --check server.js server/db.js` — ОК.
- `formatQueue` проверена узлом на примерных строках (код взят из `server.js`, `tierOf` из
  `tariffs.js`): пустая очередь → `[]`; месяц (текущий) + год (будущий) → две записи в порядке
  входа, `tier: "club"`, даты в ISO.

### Не проверено

SQL `getSubscriptionQueue` (порядок, фильтры) на базе не прогонялся — локальной БД нет. Критерий
части для аккаунта 58 (две записи в `queue`, `subscription` — только месяц) проверяется после
деплоя на живых данных.

### Замечание

`/api/auth/verify` по-прежнему отдаёт `subscription` сырой строкой БД (`expires_at`, а не
`expiresAt`, как в `/me` и `/status`) — это существовавшее расхождение, по ТЗ не менялось.

## Часть 2. /club и страница возврата

**Коммит:** `0b88906` (без push).

### Что изменено

- [`src/lib/auth.jsx`](../src/lib/auth.jsx): `queue` (по умолчанию `[]`) заполняется из `/api/auth/me`,
  `/api/subscription/status` и verify, очищается при выходе, отдаётся через контекст.
- [`src/pages/ClubPage.jsx`](../src/pages/ClubPage.jsx), блок «Тарифы»:
  - над карточками список периодов: «✓ {план}: до {дата}» для идущего и «с {дата} до {дата}» для
    будущего; триал — так же («Триал (14 дней): до …», название из `labelOf`);
  - у обеих карточек всегда кнопка: «Продлить», если в `queue` есть период этого плана
    (`club_monthly`/`monthly`, `club_yearly`/`yearly`), иначе «Оплатить»; зелёные плашки «✓ до …»
    убраны;
  - бейдж «ТЕКУЩИЙ» у карточки плана, который идёт прямо сейчас; иначе «ВЫГОДНО» у года и без бейджа
    у месяца; бейдж «ТРИАЛ» убран;
  - при непустой очереди под кнопкой серым «Новый период начнётся {максимум expiresAt по очереди}»;
  - тексты над тарифами не менялись.
- [`src/pages/PaymentReturnPage.jsx`](../src/pages/PaymentReturnPage.jsx), состояние `succeeded`:
  «{план} с {startsAt} до {expiresAt}», если `startsAt` в будущем, иначе «{план} до {expiresAt}».

### Проверка

- `npx vite build` — без ошибок.
- Реальный `ClubPage` и `PaymentReturnPage` в браузере на 390 px, API заменён заглушкой
  (`/api/auth/me` с `queue`, `/api/payments/:id`); везде `scrollWidth === innerWidth === 390`:
  - очередь из двух периодов (месяц идёт, год в очереди): список из двух строк, «ТЕКУЩИЙ» у месяца,
    «ВЫГОДНО» у года, у обеих карточек «Продлить» и «Новый период начнётся 31 октября 2027 г.»;
  - нет подписок: списка нет, у обеих «Оплатить», серой строки нет;
  - триал: строка «Триал (14 дней): до 15 октября 2026 г.», бейджей «ТРИАЛ»/«ТЕКУЩИЙ» нет, у обеих
    «Оплатить»;
  - возврат с платежом в очереди: «Клуб РПКМ · 1 год с 31 октября 2026 г. до 31 октября 2027 г.»;
    с идущим периодом: «Клуб РПКМ · 1 месяц до 1 ноября 2026 г.».
- Данные заглушки — не боевые; реальный ответ сервера (`queue` для аккаунта 58) проверяется после
  деплоя.

### Где выводится `subscription.expiresAt` (не менялись)

`HomePage.jsx:310` и `:377`, `B2BCabinetPage.jsx:105`, `ProPage.jsx:68` (часть 3), `ClubPage.jsx:150`
(плашка «Ваш статус» и «Управление подпиской»: срок текущего периода). `AdminPage.jsx:63`
использует `expiresAt` строк админки, не контекста.

### Для решения Дмитрия

Покупка Клуба при активном PRO по-прежнему ставит Клуб в хвост PRO, поведение сервера не менялось.
На `/club` у такого пользователя в списке видны PRO-период и будущий Клуб, а «Новый период начнётся»
берёт максимум по всей очереди. Особое сообщение для PRO-пользователя я не добавлял; нужно ли оно
(например, «Клуб начнётся после окончания PRO») — решает Дмитрий.

## Часть 3. /pro

**Коммит:** `c195f5a` (без push).

### Что изменено

[`src/pages/ProPage.jsx`](../src/pages/ProPage.jsx):

- Шапка при `hasPro`: рядом с плашкой «✓ PRO активен до …» кнопка «Продлить PRO за {PRO_PRICE} ₽»
  (`handlePay`), под ней серым «Период добавится к окончанию, новый срок начнётся {дата}».
- Дата берётся по последнему PRO-периоду в `queue` (максимум `expiresAt` среди `tier === 'pro'`), а не
  только по текущему; если PRO в очереди нет, запасной вариант — `subscription.expiresAt`.
- Кнопка в сравнении тарифов: при `hasPro` текст «Продлить PRO», не disabled, вызывает `handlePay`;
  при блокировке на время запроса — `disabled` только для вошедшего пользователя.
- Текст про замену Клуба на PRO показывается при `!hasPro`, как раньше.

### Побочный эффект

Переменная `expiresLabel` теперь «оплачен до» по последнему PRO и используется также в блоке
«Управление подпиской» PRO-кабинета («PRO активен до …»): там тоже показывается дата конца оплаченного
периода с учётом очереди. Доступ по-прежнему определяет `hasPro` (текущая подписка).

### Проверка

- `npx vite build` — без ошибок.
- Реальный `ProPage` в браузере, API заменён заглушкой (PRO-пользователь: текущий период и один в
  очереди; последний оканчивается 30 ноября):
  - 390 px: `scrollWidth === innerWidth === 390`; плашка, кнопка «Продлить PRO за 2 900 ₽» и серая строка
    «Период добавится к окончанию, новый срок начнётся 30 ноября 2026 г.» идут друг под другом; в
    сравнении тарифов кнопка «Продлить PRO», не disabled;
  - 1280 px: плашка и кнопка в одной строке, серая строка под ними, переполнения нет;
  - пользователь без PRO: «Оформить PRO за 2 900 ₽/мес» и «Перейти на PRO», строка про замену Клуба —
    как раньше.
- Данные заглушки не боевые; реальный `queue` проверяется после деплоя.
