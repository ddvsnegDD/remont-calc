# REPORT: понижение роли B2B при входе через B2C-форму — закрытие ТЗ

**По ТЗ:** `docs/TASK_role_downgrade.md`
**Дата проверки:** 2026-09-22
**Проверял:** чтением кода и прогоном `node --check` на рабочем дереве, коммит `b37453d`.

**Вывод коротко.** Правка выполнена ровно так, как предписывало ТЗ. Четыре критерия приёмки из пяти закрываются по коду, пятый прогоном. Один пункт из примечания к ТЗ остался непроверенным, он требует запроса к боевой БД.

---

## Что было и что стало

Дефект: в `createUser` стояло `role = COALESCE(EXCLUDED.role, users.role)`, а в параметры уходило `role || 'b2c'`. При входе через обычную форму в `EXCLUDED.role` попадало не NULL, а строка `'b2c'`, поэтому `COALESCE` выбирал её и затирал существующую роль `b2b`.

Сейчас в `server/db.js`, функция `createUser`:

```sql
ON CONFLICT (email) DO UPDATE SET
  name = COALESCE(EXCLUDED.name, users.name),
  phone = COALESCE(EXCLUDED.phone, users.phone),
  role = CASE WHEN EXCLUDED.role = 'b2b' THEN 'b2b' ELSE users.role END,
  organization = COALESCE(EXCLUDED.organization, users.organization),
  position = COALESCE(EXCLUDED.position, users.position)
```

Правило «`b2b` только повышение» реализовано именно так, как просило ТЗ.

## Что не проверено

**Восстановление роли пострадавшего аккаунта.** Примечание к ТЗ предписывало вручную выполнить на боевой БД:

```sql
UPDATE users SET role='b2b' WHERE email='ddv1121@yandex.ru';
```

Выполнялось это или нет, по коду не видно. Проверяется одним запросом на сервере:

```bash
sudo -u postgres psql -d rpkm -tAc "SELECT role FROM users WHERE email='ddv1121@yandex.ru'"
```

Ожидается `b2b`. Если вернётся `b2c`, выполнить `UPDATE` из примечания. Сама правка кода при этом уже работает и повторного понижения не допустит.

**Сквозной сценарий в интерфейсе.** Вход b2b-пользователя через B2C-модалку с последующей проверкой в админке не проигрывался. Логика разобрана по SQL, но живого прогона не было.
