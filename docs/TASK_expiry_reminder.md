# ТЗ: письмо об окончании подписки (q02)

Решения Дмитрия от 03.10.2026:
- Письмо получают и платные подписки, и триалы (Клуб-триал 14 дней, PRO-триал 7 дней).
- Отправка за 3 дня до окончания, один раз на период.
- Текст письма и правка политики конфиденциальности утверждены Дмитрием, вносятся ровно так, как написано ниже.

## Проблема

Подписка не продлевается автоматически (оферта п. 4.3). Человек узнаёт об окончании, только когда платные функции перестали работать. Планировщика в проекте нет: ни cron, ни `setInterval`, ни пакета `node-cron`. Серверный процесс один (PM2 `rpkm`, режим fork), поэтому внутренний таймер не даст дублей, но отметка «письмо отправлено» нужна, иначе перезапуск процесса (а их бывает несколько в день при деплоях) отправит письмо повторно.

## Что сделать

Два отдельных коммита, в таком порядке. После обоих: `node --check` для затронутых серверных файлов, `npx vite build`, не пушить, остановиться, отчёт в docs/REPORT_expiry_reminder.md.

### Часть 1. Политика конфиденциальности (коммит 1)

**src/pages/PrivacyPage.jsx**, раздел 3 «Цели обработки», пункт «Направления транзакционных уведомлений (код авторизации, информация об оплате)». Заменить на: «Направления транзакционных уведомлений (код авторизации, информация об оплате, уведомление об окончании срока подписки)».

Дата внизу страницы (~133): «Дата последнего обновления: 3 октября 2026 г.»

Больше в политике ничего не менять. Согласие (ConsentPage.jsx) не трогать: цель «Связь со мной по вопросам работы сервиса и подписки» там уже есть.

### Часть 2. Письмо и таймер (коммит 2)

**2.1. Число.** В `src/data/tariffs.js` добавить `export const EXPIRY_REMINDER_DAYS = 3;` рядом с другими лимитами. Сервер уже импортирует оттуда `PLANS, tierOf, daysOf, labelOf`, добавить импорт константы. Цифру 3 нигде больше не писать.

**2.2. Схема БД.** В `initDB()` (server/db.js, рядом с другими `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, строки ~27-38 и ~72):
`ALTER TABLE subscriptions ADD COLUMN IF NOT EXISTS expiry_reminder_sent_at TIMESTAMPTZ;`
Колонка обнуляемая, без значения по умолчанию, существующие строки получат NULL.

**2.3. Выборка и отметка (server/db.js).** Две новые экспортируемые функции:

- `findExpiringSubscriptions(days)`: подписки, у которых `status IN ('trial','active')`, `started_at <= NOW()`, `expires_at > NOW()`, `expires_at <= NOW() + INTERVAL '1 day' * $1`, `expiry_reminder_sent_at IS NULL`. Вернуть вместе с `users.id`, `users.email` (JOIN по `user_id`). Подписки с `user_id IS NULL` пропускать.
- `claimReminder(subscriptionId)`: `UPDATE subscriptions SET expiry_reminder_sent_at = NOW() WHERE id = $1 AND expiry_reminder_sent_at IS NULL RETURNING id`. Вернуть `true`, если строка обновилась. Это захват перед отправкой: два параллельных прогона не отправят письмо дважды.
- `releaseReminder(subscriptionId)`: `UPDATE subscriptions SET expiry_reminder_sent_at = NULL WHERE id = $1`. Вызывается, если отправка не удалась, чтобы следующий прогон попробовал снова.

**2.4. Правило «письмо не нужно» (server.js).** Для каждой найденной подписки получить `getSubscriptionQueue(user_id)` (уже есть в db.js, возвращает все периоды `trial/active` с `expires_at > NOW()`). Пропустить подписку, если в очереди есть другой период с `expires_at` позже текущего и уровнем не ниже текущего (ранг: club = 1, pro = 2, уровень через `tierOf(plan)`). Смысл: у человека уже оплачено продолжение, письмо «заканчивается» было бы ложным. Пример: PRO-триал заканчивается, в очереди PRO на месяц, письма нет. Пример наоборот: PRO заканчивается, дальше в очереди только Клуб, письмо уходит, потому что PRO-функции пропадут.
Пропущенные таким образом подписки отметкой НЕ помечать (если очередь изменится, например вернут деньги за следующий период, письмо уйдёт на следующем прогоне).

**2.5. Отправка (server.js).** Функция `runExpiryReminders()` рядом с другими функциями писем:
1. Если `dbReady` ложь, выйти.
2. Взять список из `findExpiringSubscriptions(EXPIRY_REMINDER_DAYS)`, отфильтровать по 2.4.
3. Для каждой: `claimReminder(id)`. Если `false`, пропустить. Иначе отправить письмо через `sendRawEmail(email, subject, html)`. Если вернулось `false` или было исключение, вызвать `releaseReminder(id)`.
4. Каждый шаг в `try/catch`, одна ошибка не должна ронять прогон и остальные письма.
5. В лог: одна строка на прогон, только если что-то нашлось: сколько найдено, пропущено по 2.4, отправлено, не удалось. Адреса электронной почты в лог не писать, только id подписки.

**2.6. Таймер (server.js, внутри `start()` после `app.listen`).**
- Прогон через 2 минуты после старта (`setTimeout`) и дальше раз в час (`setInterval`, 60 * 60 * 1000 мс).
- Флаг «прогон идёт»: если прошлый ещё не закончился, новый пропустить.
- Запускать только если `dbReady`.
- Новых зависимостей не добавлять.

**2.7. Текст письма (утверждён).**

Тема: `Подписка РПКМ заканчивается {дата}`, дата без года, по Москве: «10 октября» (`toLocaleDateString('ru-RU', { day: 'numeric', month: 'long', timeZone: 'Europe/Moscow' })`).

Тело:

> Здравствуйте!
>
> Ваш доступ «{название плана}» действует до {дата с годом} г. После этой даты платные функции станут недоступны.
>
> Чтобы продолжить, оформите новый период на странице {Клуба / PRO}: {ссылка}
>
> Подписка не продлевается автоматически, деньги без вашего действия не списываются. Если продлевать не нужно, ничего делать не требуется.
>
> Вопросы по подписке: ddv1121@yandex.ru
>
> РПКМ · Калькулятор ремонта

Подстановки:
- Название плана: `labelOf(plan)`, через `escapeHtml`.
- Дата с годом: `toLocaleDateString('ru-RU', { day: 'numeric', month: 'long', year: 'numeric', timeZone: 'Europe/Moscow' })`, затем `.replace(/\s+г\.$/, ' г.')` (так же, как на страницах).
- Страница: `tierOf(plan) === 'pro'` → «страницы PRO» и `${SITE_URL}/pro`; иначе «страницы Клуба» и `${SITE_URL}/club`. Ссылка кликабельная.
- Оформление: инлайн-стили в духе письма с кодом входа (`sendAuthCode`, server/email.js): шрифт Inter/Arial, цвет акцента #B95C38, подвал серым мелким шрифтом. Кнопок и картинок нет, только текст и одна ссылка.
- Ничего рекламного не добавлять: ни скидок, ни призывов «успейте», ни упоминания консультаций и других возможностей.
- Никаких обещаний про сохранность данных после окончания подписки в тексте нет, и добавлять их нельзя.

## Что не трогать

- Логику подписок, очереди, триала, возвратов и платежей (server/db.js, кроме двух новых функций и одной колонки).
- Тарифы, цены и лимиты в `src/data/tariffs.js`, кроме новой константы.
- Письма об оплате, консультациях, коды входа.
- Оферту и согласие.
- Страницы /club и /pro.

## Критерии приёмки

1. `node --check server.js server/db.js` и `npx vite build` проходят.
2. В политике изменены только пункт раздела 3 и дата, остальной текст идентичен.
3. Число дней берётся только из `EXPIRY_REMINDER_DAYS`, поиск по `src` и `server` не находит другой тройки, привязанной к напоминанию.
4. Колонка `expiry_reminder_sent_at` добавлена одним `ADD COLUMN IF NOT EXISTS`, повторный запуск `initDB()` безопасен.
5. Порядок в `runExpiryReminders`: захват отметки, затем отправка, при неудаче снятие отметки. Нет пути, при котором письмо уходит без отметки.
6. Правило 2.4 учитывает уровень: очередь из Клуба не гасит письмо об окончании PRO.
7. В логах нет адресов электронной почты.
8. В отчёте: что именно считается в `findExpiringSubscriptions`, как проверялась логика пропуска (хотя бы разбор трёх сценариев на бумаге: платная без очереди, триал с оплаченным продолжением, PRO с очередью из Клуба), список изменённых файлов, хеши двух коммитов.
