# ТЗ: уровни детальной сметы — состав вместо коэффициентов

## Проблема

Детальная смета (`SpecCalc.compute`, `src/lib/spec-calculator.js`) даёт для квартиры
60 м², новостройка-монолит, без отделки, полный цикл:

| | ₽/м² |
|---|---|
| Квиз `capital` (вилка рынка) | 37 853 — 59 483 |
| Детальная `capital` | 82 550 |

Превышение верха вилки — **+39 %**. Цель — 10–15 %.

Причина не в ценах позиций: расценки взяты из реальных тендерных смет и верны.
Причина в **составе**. `SPEC_DATA.full` — это один конкретный объект (евроремонт),
где все 180 м² стен обшиты ГКЛ по каркасу в два слоя и дополнительно утеплены,
а потолок — подвесной ГКЛ. `TIER_MULTIPLIERS` при этом трогает только `finish` и
`sanitary`, а 41 % денег лежит в `rough`:

| класс | ₽ | доля |
|---|---|---|
| rough (конструктив) | 2 034 890 | 41,1 % |
| finish | 998 807 | 20,2 % |
| prep (подготовка) | 693 183 | 14,0 % |
| doors | 456 527 | 9,2 % |
| terminal (оконечка) | 315 198 | 6,4 % |
| windows | 180 336 | 3,6 % |
| engineering (магистрали) | 174 049 | 3,5 % |
| sanitary (магистрали) | 100 000 | 2,0 % |

**Доказательство, что одними коэффициентами задача не решается.** Понижающие
на `prep`, материалы `finish` и материалы `terminal` — даже жёсткие — дают:

| коэффициенты | результат | к верху вилки |
|---|---|---|
| prep 0,85 / finish mp 0,80 / term mp 0,70 | 79 387 ₽/м² | +33 % |
| prep 0,75 / finish mp 0,65 / term mp 0,55 | 77 322 ₽/м² | +30 % |
| prep 0,65 / finish mp 0,50 / term mp 0,45 | 75 365 ₽/м² | +27 % |

Ниже +27 % коэффициенты не опускают, потому что деньги не там. А чтобы
опустить сильнее, пришлось бы занижать сами расценки — то есть врать в цифре,
которую пользователь потом понесёт подрядчику.

**Что решает.** Смена состава `rough` для уровня «Капитальный»:

| вариант | результат | к верху вилки |
|---|---|---|
| только убрать утепление стен | 76 246 ₽/м² | +28 % |
| ГКЛ стен → штукатурка, утепление оставить | 73 822 ₽/м² | +24 % |
| **ГКЛ стен → штукатурка + убрать утепление** | **67 518 ₽/м²** | **+14 %** |
| то же + потолок без ГКЛ | 62 797 ₽/м² | +6 % |

Третий вариант попадает в целевой коридор при коэффициентах = 1. То есть
коэффициенты из этого ТЗ становятся точной подстройкой, а не основным рычагом.

---

## Решение по составу (подтверждено Дмитрием 23.09.2026)

> Для уровня «Капитальный» в жилых помещениях стены **штукатурятся по маякам**
> (расценка берётся из существующей позиции «Штукатурка стен толщиной до 20 мм
> по сетке», 2 486 ₽/м² работа+материал), а не обшиваются ГКЛ по каркасу;
> **утепление стен не выполняется**; потолок остаётся подвесным ГКЛ.

Подтверждено. Расценку штукатурки брать из существующей позиции, новых цифр
не придумывать.

## Часть 2. Переименование уровней

Текущий набор `SPEC_DATA.full` — это **евроремонт**, а не капитальный. Сейчас он
подписан как `capital` с множителями 1,0, а `euro` получает надбавку сверху.
Это перевёрнуто.

Целевая модель:

| tier | набор позиций | множители |
|---|---|---|
| `cosmetic` | **новый набор** (часть 4) | все 1,0 |
| `capital` | `full` со сменой состава (часть 3) + понижающие | часть 3 |
| `euro` | `full` как есть | все 1,0 |
| `premium` | `SPEC_DATA.premium` как есть | без изменений |

`TIER_LABELS` дополнить: `cosmetic: 'Косметический'`.

**Обратная совместимость.** `tierKey` в `SpecCalc.compute` сейчас падает на
`'capital'` при неизвестном уровне — оставить. Квиз (`B2CQuizPage.jsx`) мапит
`repair_type` через `tierMap`, где `cosmetic → capital`; после этого ТЗ маппинг
должен стать прямым: `cosmetic → cosmetic`.

## Часть 3. Уровень «Капитальный»

Строится из того же `SPEC_DATA.full` двумя механизмами.

### 3.1. Смена состава

Нужен механизм подмены позиций по уровню. Предлагаемая форма — отдельный
экспорт в `src/lib/spec-data.js`, чтобы не дублировать массив позиций:

```js
export const TIER_COMPOSITION = {
  capital: {
    // позиции, исключаемые из набора (сверка по name + unit)
    exclude: [
      { name: 'Облицовка стен из гипсокартона/фанеры в два слоя по металлическому каркасу', unit: 'м2' },
      { name: 'Устройство утепления стен', unit: 'м2' },
    ],
    // позиции, добавляемые взамен
    add: [
      { g:'05.05.02.06', sub:'05.05.02.06.02', name:'Штукатурка стен толщиной до 20 мм по сетке',
        mat:'Штукатурная смесь, сетка, маяки', unit:'м2', vol:'area*3', wp:<из поз.43>, mp:<из поз.43>, cls:'rough' },
    ],
  },
};
```

`wp`/`mp` для добавляемой позиции **взять ровно из существующей поз. 43**
(штукатурка в санузле) — не придумывать новые цифры. `vol` — та же формула,
что у исключаемой облицовки ГКЛ (сверить по факту в данных, ожидается `area*3`).

В `SpecCalc.compute` применять `TIER_COMPOSITION[tierKey]` к `items` до цикла
расчёта. Для уровней без записи в `TIER_COMPOSITION` набор не меняется.

### 3.2. Понижающие коэффициенты

Добавить в `TIER_MULTIPLIERS.capital`. Значения **подбираются эмпирически**:
после реализации частей 1–3.1 я прогоняю варианты и присылаю цифры, Дмитрий
выбирает. Стартовая гипотеза для первого прогона:

```js
capital: {
  rough:       { wp: 1.00, mp: 1.00 },
  prep:        { wp: 0.90, mp: 0.90 },   // 1 слой шпатлёвки вместо 2, без стеклохолста
  finish:      { wp: 1.00, mp: 0.85 },   // финишный материал дешевле
  terminal:    { wp: 1.00, mp: 0.70 },   // оконечка эконом-сегмента
  engineering: { wp: 1.00, mp: 1.00 },
  sanitary:    { wp: 1.00, mp: 1.00 },
  doors:       { wp: 1.00, mp: 1.00 },
  windows:     { wp: 1.00, mp: 1.00 },
}
```

Для `euro` все восемь классов = 1,00 (текущие надбавки 1,30/2,00 снимаются —
теперь `full` и есть евроремонт).

## Часть 4. Уровень «Косметический» — новый набор позиций

Новый массив `SPEC_ITEMS_COSMETIC` в `src/lib/spec-data.js`, экспортируется как
`SPEC_DATA.cosmetic`. Состав по постановке Дмитрия:

**Включается:**
- заделка трещин (новая позиция, расценки уточнить у Дмитрия);
- шпатлёвка стен и потолков **в один слой** (взять поз. 21 и 25, `wp`/`mp` × 0,55
  — уточнить множитель у Дмитрия, либо дать отдельные расценки);
- грунтовка стен и потолков (поз. 20, 24 без изменений);
- окраска стен и потолков за 2 раза (поз. 22, 27 без изменений);
- замена финишного покрытия пола (поз. 34 ламинат, 35 плинтус) и демонтаж старого
  (новая позиция);
- замена оконечки: поз. 1–4, 6–9, 11–13, 15 — то есть весь класс `terminal`.

**Не включается:**
- двери (`doors`) — по прямому указанию: «даже двери не трогаем»;
- окна (`windows`);
- весь конструктив `rough`: перегородки, ГКЛ-потолки, облицовка ГКЛ, утепление,
  стяжки, гидроизоляция, стеклянные перегородки;
- магистрали `engineering` и `sanitary` (кабель, щит, трубы);
- плитка (поз. 30, 44, 49) и штукатурка (43).

`SPEC_GROUPS` переиспользуются — новые группы не заводить, позиции раскладываются
по существующим `prefix`.

**Что нужно от Дмитрия до реализации части 4:** расценки (`wp`/`mp`) на две новые
позиции — «Заделка трещин» и «Демонтаж существующего покрытия пола» — и решение
по шпатлёвке в один слой (отдельная расценка или множитель к двухслойной).
Часть 4 делается **после** частей 1–3, отдельным заходом.

## Не трогать

- Расценки `wp`/`mp` существующих позиций — они из реальных тендерных смет.
  Уровни отличаются составом и множителями, но не подменой самих расценок.
- `SPEC_DATA.premium` и `SPEC_GROUPS_PREMIUM`.
- `src/data/replan.js` и порядок применения резерва/перепланировки
  (`RESERVE_BEFORE_REPLAN`) — сделано в `calc_input_hardening`.
- Квизовый движок `calculateB2C` и вилки `TIERS` в `src/lib/calculator.js` —
  вилка это анализ рынка, она эталон, под неё подгоняется детальная смета,
  а не наоборот.
- `SPEC_DATA.whitebox` — состав меняем только там, где переклассификация `cls`
  (часть 1); уровневой подмены для whitebox не вводим.

## Критерии приёмки

1. В `SPEC_ITEMS_FULL` нет позиций с `cls: 'rough'` из списка 1.1 — у них `cls: 'prep'`;
   нет позиций из списка 1.2 с `cls: 'sanitary'`/`'engineering'` — у них `cls: 'terminal'`.
   Суммарное число позиций не изменилось (50 в `full`).
2. `SpecCalc.compute` с `tier: 'euro'` даёт **тот же итог, что сейчас даёт
   `tier: 'capital'`** — 4 952 991 ₽ (82 550 ₽/м²) для 60 м²/1 с/у/3 окна/2 комнаты,
   полный цикл, без перепланировки. Это контроль, что переименование не сдвинуло цифру.
3. `SpecCalc.compute` с `tier: 'capital'` при множителях 1,0 и включённой сменой
   состава даёт 67 518 ₽/м² ± 100 ₽ на том же наборе входов.
4. `TIER_MULTIPLIERS` для каждого уровня перечисляет все восемь классов явно.
5. `TIER_LABELS.cosmetic === 'Косметический'`; `tierMap` в `B2CQuizPage.jsx`
   больше не схлопывает `cosmetic` в `capital`.
6. `npx vite build` проходит без ошибок.
7. Отчёт `docs/REPORT_spec_tiers.md` с итоговой таблицей ₽/м² по всем уровням
   (`cosmetic`/`capital`/`euro`/`premium`) против вилок квиза для одного и того же
   набора входов.

## Порядок работ

1. Часть 1 (переклассификация) — проверяется критерием 1.

   **Важно, уточнено 23.09.2026 по ходу работы.** Часть 1 не является
   число-нейтральной для уровня `euro`, и это нормально. Восемь из двенадцати
   позиций, уезжающих в `terminal`, раньше лежали в `sanitary`, где у `euro`
   стоит множитель на материалы 2,00; четыре остальные пришли из `engineering`
   с множителем 1,00. Один множитель `terminal` не может сохранить оба
   поведения сразу — по построению. Поэтому после части 1:
   - `capital` обязан остаться **ровно прежним**: 4 952 991 ₽ (82 550 ₽/м²)
     на 60 м² / 1 с/у / 3 окна / 2 комнаты, полный цикл, без перепланировки.
     Его множители и так все единицы, сдвигаться неоткуда. Это и есть контроль
     правильности переклассификации.
   - `euro` сдвинется вниз на 76 451 ₽ (с 5 566 965 до 5 490 514 ₽,
     92 783 → 91 509 ₽/м²) — ровно сумма `mp` восьми перенесённых позиций
     сантехники, потерявших надбавку ×2. Компенсирующий множитель не вводить:
     в части 2 `euro` всё равно приводится к набору с единичными множителями
     и приходит к 4 952 991 ₽. Костыль пришлось бы снимать на следующем шаге.
2. Часть 2 + 3.1 (переименование и смена состава) — проверяется критерием 3.
3. Пауза: я прогоняю варианты коэффициентов, Дмитрий выбирает.
4. Часть 3.2 (коэффициенты) — вписываются выбранные значения.
5. Часть 4 (косметический) — отдельным ТЗ после получения расценок.
