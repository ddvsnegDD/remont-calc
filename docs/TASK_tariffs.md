# ТЗ: разделение тарифов Клуб / PRO, новые цены, реальная оплата PRO

## Контекст и проблемы

1. **Планов PRO не существует.** В `server.js` объект `PLANS` содержит только `monthly` (490 ₽/30д) и `yearly` (4900 ₽/365д) — оба B2C («Клуб РПКМ»). Из-за этого подписка, выданная PRO-пользователю, отображается как «Годовой (4 900 ₽/год)».
2. **Страница `/pro` — демо.** Кнопка «Оформить PRO» ставит локальный стейт (`setSubscribed(true)`), реальной оплаты нет, повсюду подписи «(демо)».
3. **Доступ не разделён.** `hasAccess` в `src/lib/auth.jsx` = любая подписка `active`/`trial`. Значит подписчик Клуба получает PRO-функции (офисный калькулятор), которые продаются дороже.
4. **Цены захардкожены** в `HomePage.jsx`, `ClubPage.jsx`, `ProPage.jsx`, `B2CDetailPage.jsx`, `ProPaywall.jsx`, `OfferPage.jsx` — единого источника нет.

## Целевая тарифная сетка

| План | Уровень | Цена | Срок |
|---|---|---|---|
| Клуб · месяц | `club` | **99 ₽** | 30 дней |
| Клуб · год | `club` | **990 ₽** | 365 дней |
| PRO · месяц | `pro` | **2 900 ₽** | 30 дней |

Триал 14 дней — уровень `club`.

**Уровни доступа:**
- `club` — чек-листы приёмки, детальная смета квартиры (B2C), консультации;
- `pro` — всё из `club` **плюс** офисный fit-out калькулятор и детальная спецификация B2B.

То есть PRO включает возможности Клуба, обратное — нет.

## Часть 1. Единый источник тарифов

Создать `src/data/tariffs.js` — единственный источник правды по планам:

```js
export const PLANS = {
  club_monthly: { id: 'club_monthly', tier: 'club', price: 99,   days: 30,  label: 'Клуб РПКМ · 1 месяц' },
  club_yearly:  { id: 'club_yearly',  tier: 'club', price: 990,  days: 365, label: 'Клуб РПКМ · 1 год' },
  pro_monthly:  { id: 'pro_monthly',  tier: 'pro',  price: 2900, days: 30,  label: 'РПКМ PRO · 1 месяц' },
};
```

- `server.js` импортирует этот файл напрямую (проект ESM, фронтенду не доверяем — цены берём из него на бэке).
- Все страницы берут цены отсюда, хардкод `490` / `4 900` / `2 900` убрать.

**Обратная совместимость (обязательно):** в БД уже есть подписки с `plan` = `monthly`, `yearly`, `trial`. Их нужно трактовать как уровень `club`; для `trial` — тоже `club`. Добавить хелпер вида `tierOf(plan)`, который маппит legacy-значения. Существующие подписки не мигрировать.

## Часть 2. Разделение доступа

`src/lib/auth.jsx`:
- вычислять `tier` активной подписки (`club` | `pro` | null);
- отдавать в контексте `hasClub` (tier `club` или `pro`) и `hasPro` (только `pro`);
- `hasAccess` оставить как алиас `hasClub` для обратной совместимости существующего кода.

Применение:
- **PRO-функции** (`B2BResultPage` — детальная спецификация, `B2BOfficePage`, `B2BOfficeResultPage`, `B2BOfficeDetailPage`, кнопка «+ Офис PRO» в `B2BCabinetPage`) → проверять `hasPro`;
- **Клубные функции** (`B2CDetailPage` — детальная смета квартиры, чек-листы, `ClubPage`) → проверять `hasClub`;
- Пейволл `ProPaywall` должен вести на `/pro` для PRO-функций и на `/club` для клубных (добавить проп, например `target`).

Бэкенд: в `/api/subscription/status` и `/api/auth/me` добавить в объект подписки поле `tier`.

## Часть 3. Реальная оплата PRO

- `PLANS` на бэке теперь включает `pro_monthly` → эндпоинт `POST /api/subscription/pay` начинает принимать этот план без отдельной логики (сумма и label берутся из `PLANS`).
- `successURL` формировать по уровню плана: для `pro_*` → `${SITE_URL}/pro?payment=success&label=...`, для `club_*` → `/club?...` (сейчас всегда `/club`).
- `activateSubscription(label)` в `server/db.js` сейчас хардкодит 30 дней и отдельно проверяет `plan === 'yearly'` для 365. Переписать: срок брать из `PLANS[plan].days`, с фолбэком 30 для legacy-планов (`monthly` → 30, `yearly` → 365).
- `src/pages/ProPage.jsx`: убрать демо-логику (`setSubscribed`, все подписи «(демо)»), кнопку «Оформить PRO» подключить к тому же потоку оплаты, что и `ClubPage` (`POST /api/subscription/pay` → редирект на `paymentUrl` → возврат с `?payment=success` → поллинг статуса). Статус PRO показывать из `hasPro`/`subscription`, а не из локального стейта.
- Блоки-заглушки на `/pro` («White-label PDF», «Экспорт CSV», «Персональный менеджер») пока оставить как есть, но заменить формулировку «в демо не реализовано» на «скоро» — чтобы не выглядело демонстрационным на боевом сайте.

## Часть 4. Админка — выдача подписки по уровню

`src/pages/AdminPage.jsx` + `POST /api/admin/users/:id/subscription`:
- при ручной выдаче спрашивать не только срок в днях, но и уровень: **Клуб** или **PRO** (например, два пункта в prompt или две кнопки);
- в `grantSubscription(userId, plan, days)` передавать конкретный план из `PLANS` (`club_yearly`, `pro_monthly` и т.п.);
- в таблицах админки в колонке «Подписка» рядом со статусом показывать уровень (Клуб / PRO).

## Часть 5. Обновить цены в текстах

Заменить старые цифры на новые (99 / 990 / 2 900) везде, где они выводятся:
`HomePage.jsx`, `ClubPage.jsx` (в т.ч. строка вида «План: Годовой (4 900 ₽/год)»), `B2CDetailPage.jsx`, `ProPaywall.jsx`, `ProPage.jsx`.

**Отдельно — `src/pages/OfferPage.jsx` (юридический документ):** в разделе «Тарифные планы и стоимость» указать актуальную сетку: Клуб — 99 ₽/мес и 990 ₽/год, PRO — 2 900 ₽/мес; сохранить пункт про бесплатный триал 14 дней и обновить дату публикации.

## Не трогать
- Механику ЮMoney-вебхука и проверку подписи.
- Схему таблицы `subscriptions` (миграции не нужны — legacy-планы обрабатываются маппингом).
- Существующие подписки в БД.

## Критерии приёмки
1. Цены на сайте: Клуб 99 ₽/мес и 990 ₽/год, PRO 2 900 ₽/мес; старых 490/4900 в интерфейсе и оферте не осталось.
2. Подписчик Клуба **не** получает офисный калькулятор и детальную спецификацию B2B — видит пейволл с CTA на `/pro`.
3. Подписчик PRO получает и PRO-функции, и клубные.
4. Пользователь с legacy-подпиской (`plan = 'yearly'`, как сейчас у ddv1121@yandex.ru) не теряет доступ — трактуется как Клуб.
5. Кнопка «Оформить PRO» ведёт на реальную оплату ЮMoney; после оплаты вебхук активирует подписку с уровнем `pro` и сроком 30 дней.
6. В админке можно выдать подписку уровня Клуб или PRO; уровень виден в таблице.
7. `node --check server.js server/db.js` и `npx vite build` проходят без ошибок.
