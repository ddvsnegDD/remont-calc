## Критерии приёмки — фактический результат

**Среда проверки:** MacBook Air, нет `.env` и локального PostgreSQL. Backend поднимался вручную (`PORT=3001`, тестовые `JWT_SECRET`/`ADMIN_PASSWORD` через переменные окружения, без БД), фронт — `npm run dev` (vite, порт 3000, прокси `/api` → :3001), проверка через встроенный браузер. Оба процесса остановлены после проверки.

1. **Залогиненный без подписки на `/checklists` видит пейволл с кнопкой на `/club`, не список.**
   **Не проверено end-to-end.** `/api/auth/me` (эндпоинт, которым `AuthProvider` проверяет сессию при монтировании) сам по себе не за `requireDB`, но внутри вызывает `findUserByEmail`/`getActiveSubscription`, которые без БД падают в `catch` → 500. Фронт трактует любой не-`ok` ответ как «не залогинен» (`r.ok ? r.json() : null`), так что состояние «залогинен, но без подписки» получить через реальный логин на этой машине нельзя в принципе — залогиниться самому уже не выходит без БД. Корректность ветки подтверждена только чтением кода и порядком проверок (см. диф выше): `!hasClub` стоит после `!user`, значит сработает для любого залогиненного без `hasClub`.

2. **Тот же пользователь по прямой ссылке `/checklists/<id>` видит тот же пейволл.**
   **Не проверено end-to-end** по той же причине (нет способа залогиниться без БД). Структурно проверено: ветка `if (!hasClub)` добавлена в `ChecklistDetailPage.jsx` отдельно от списка, с тем же условием и тем же компонентом — не «заодно» с списком, как и требовало ТЗ.

3. **Незалогиненный видит прежнее приглашение войти, текст не изменился.**
   **Выполнено, проверено вживую.** Открыл `/checklists` и `/checklists/floor` (валидный id из `src/data/checklists.js`) без сессии:
   ```
   /checklists       → "Чек-листы приёмки работ / Авторизуйтесь, чтобы использовать интерактивные чек-листы / Войти"
   /checklists/floor → "Авторизуйтесь для доступа / Войти"
   ```
   Тексты совпадают с тем, что было в файлах до правки (ветки `if (!user)` не редактировались). Ошибок в консоли, связанных с рендером, нет.

4. **Пользователь на триале видит чек-листы и может с ними работать.**
   **Не проверено — нужна БД.** Логически: триал даёт `tier === 'club'` (через `LEGACY_TIER`/`tierOf` в `src/data/tariffs.js`, см. п. 3 ТЗ), значит `hasClub` будет `true`, и ветка `if (!hasClub)` для триала не сработает. Это следует из формулы `hasClub = tier === 'club' || tier === 'pro'` в `src/lib/auth.jsx`, которую я не менял. Живого триального пользователя создать не на чем.

5. **Подписчик Клуба и подписчик PRO видят чек-листы.**
   **Не проверено — нужна БД.** Аналогично п. 4: для обоих `hasClub === true` по той же формуле, ветка пропускает их к контенту. Живьём не воспроизведено.

6. **При загрузке страницы пейволл не мелькает — виден лоадер.**
   **Проверено частично.** Ветка `authLoading` стоит первой в обоих файлах, до `!user` и до `!hasClub` — это видно из дифа и гарантирует, что ни форма входа, ни пейволл не могут отрендериться раньше лоадера ни при каком состоянии `user`/`hasClub`, потому что React не дойдёт до этих веток, пока `authLoading` истинно. `loading` в `src/lib/auth.jsx` стартует с `useState(true)`, то есть на первом кадре всегда `true`.
   Живьём поймать сам момент мигания не удалось: локально `GET /api/auth/me` отвечает быстрее миллисекунды (видно по сетевым логам — интервалы между запросом и следующим в пределах 1–2 мс), так что окно для скриншота физически не поймать инструментами браузера, которые есть в сессии. Это не потому что логика не работает, а потому что не на чем создать задержку без БД или без правки прод-конфига сети.

7. **Заполненный чек-лист не теряется при отзыве/возврате подписки.**
   **Не проверено сценарием из ТЗ** (заполнить → отозвать через `/admin` → проверить закрытие → вернуть → проверить сохранность) — весь сценарий требует реальной подписки и `/admin` с БД, которых здесь нет.
   Что проверено вместо этого — статически, чтением кода: `getStorageKey(userId, checklistId)` и вся работа с `localStorage` в обоих файлах не менялась ни строкой (см. «Не тронуто» выше). Ветка `if (!hasClub)` — это `return` до того, как компонент вообще обращается к `localStorage` (загрузка состояния в `ChecklistDetailPage.jsx` происходит в `useEffect` ниже по файлу, до неё дело не доходит, пока `!hasClub`). Значит закрытие страницы не может стереть данные — оно просто не даёт компоненту вообще инициализировать эту логику, пока подписки нет. Но это вывод из чтения кода, а не из наблюдения за реальным поведением с настоящими данными в браузере.

## Отдельно: подтверждение сохранности данных (п. 7)

Полный живой сценарий («заполнить → отозвать подписку → проверить закрытие → вернуть подписку → проверить сохранность отметок») **не пройден** — он требует одновременно рабочей БД (для реальной подписки и `/admin`) и залогиненного пользователя, ни то ни другое на этой машине недоступно.

Вместо этого — статическая гарантия из самого дифа:

- Правка не трогает ни `getStorageKey`, ни `loadState`/`saveState` (в `ChecklistDetailPage.jsx`), ни `getProgress` (в `ChecklistsPage.jsx`) — эти функции остались байт в байт как были, `git diff` по обоим файлам это подтверждает.
- Новая ветка `if (!hasClub)` — это ранний `return` компонента. Она стоит до `useEffect`, который вызывает `loadState`/`getProgress`, и до любого кода, который читает или пишет `localStorage`. Значит при потере доступа компонент просто не рендерит форму чек-листа и не трогает хранилище — ни читает, ни очищает.
- Ключ в `localStorage` (`rpkm_checklist_${userId}_${checklistId}`) не зависит от статуса подписки, только от `userId` и `checklistId` — то есть данные того же пользователя останутся под тем же ключом и найдутся, когда `hasClub` снова станет `true` и компонент снова дойдёт до чтения.

Это даёт разумную уверенность в сохранности данных на уровне кода, но не заменяет тест из критерия 7. Рекомендация: прогнать этот сценарий на стейджинге или сразу после деплоя на боевой (где есть БД), прежде чем считать пункт 7 закрытым окончательно.

## Что не удалось проверить и почему

Общая причина — как и в предыдущем ТЗ (`docs/REPORT_admin_access_hardening.md`): на этой машине нет `.env` и локального PostgreSQL. В этот раз ограничение жёстче: даже вход обычного пользователя (`/api/auth/send-code`, `/api/auth/verify`) и восстановление сессии (`/api/auth/me`) требуют БД, поэтому состояние «я залогинен» для B2C/B2B-пользователя вообще недостижимо локально — не только «с подпиской», но и «без подписки».

Непроверенное:
- Критерий 1 — пейволл для залогиненного без подписки на `/checklists`.
- Критерий 2 — тот же пейволл по прямой ссылке `/checklists/<id>`.
- Критерий 4 — доступ для триала.
- Критерий 5 — доступ для подписчиков Клуба и PRO.
- Критерий 6 — сам момент отсутствия мигания (логика проверена по коду, но не поймана вживую: локальный ответ `/api/auth/me` быстрее миллисекунды).
- Критерий 7 — полный сценарий сохранности данных при отзыве/возврате подписки (дана только статическая гарантия по коду, см. раздел выше).

Всё это требует окружения с рабочей БД — staging или боевой сервер. Рекомендую прогнать сценарий из критерия 7 в первую очередь после деплоя, поскольку это единственный пункт, где по ошибке можно потерять данные пользователя, а не просто увидеть неправильный экран.
