# ТЗ: перенос пользовательских данных из браузера на сервер

**Дата:** 2026-09-25.
**Куда положить:** `docs/TASK_server_storage.md`.
**Основание:** боевая проверка 25.09.2026 и разведка `docs/RECON_server_storage.md` (коммит `a4c8c48`). Номера строк ниже взяты оттуда, перед правкой сверять по якорям.

Большое ТЗ. Делается частями, **каждая часть отдельным коммитом**, ревью диффа после каждой части. Деплой один, после всех частей, по отдельной команде.

## Проблема

Удаление аккаунта в админке стирает только то, что лежит в базе: пользователя, коды входа, подписки. Всё остальное, что человек делает на сайте, живёт в браузере, и сервер о нём не знает.

1. **Расчёты профи** лежат в `localStorage` под одним общим ключом `rpkm-b2b-calcs`, без id пользователя (`B2BQuizPage.jsx:141`, `B2BOfficePage.jsx:122`, `B2BCabinetPage.jsx:44,58`). Кабинет показывает весь массив любому, кто вошёл на этом устройстве. Удалённый аккаунт, зарегистрированный заново, видит свои старые расчёты; другой человек на том же компьютере видит чужие. Плашка в кабинете при этом обещает «NDA активен».
2. **Чек-листы** лежат в `localStorage` под ключом с `userId` (`ChecklistDetailPage.jsx:17,24`, `ChecklistsPage.jsx:18,52`). Чужой их не увидит, но при удалении аккаунта они остаются на устройстве, на другое устройство не переходят. Фото хранятся как base64 прямо в том же объекте (`compressImage`, `ChecklistDetailPage.jsx:27-47`), без лимита (`addPhoto`, строки 252-257). Хранилище браузера у сайта около 5 МБ, после нескольких десятков фото `setItem` падает, а вызван он без `try/catch` (строки 23-25): пользователь теряет фотофиксацию молча.
3. **Счётчик консультаций** считается только в браузере (`ClubPage.jsx:67,88`), сервер его не проверяет (`POST /api/consultation`, `server.js:332-356`). Очистка браузера обнуляет лимит.
4. **`sessionStorage` не чистится при выходе** (`logout`, `src/lib/auth.jsx:81-85`). Второй человек в той же вкладке открывает страницу результата и видит расчёт первого (`rpkm-last-b2c`, `rpkm-last-b2c-detail`, `rpkm-b2b-current`, `rpkm-b2b-office-current`). `trialUsed` тоже не сбрасывается.
5. **Лимит «3 расчёта/мес» у бесплатного профи** есть только в тексте (`B2BCabinetPage.jsx:96`, `B2BProfilePage.jsx:61,122`), в коде не считается.
6. **Попутный баг:** кнопка «Открыть» у офисного расчёта в кабинете пишет в `rpkm-b2b-current` (`B2BCabinetPage.jsx:162`), а ведёт на `/b2b-office-result`, которая читает `rpkm-b2b-office-current` (`B2BOfficeResultPage.jsx:26`). Офисный расчёт из кабинета не открывается.
7. **`deleteUser`** (`server/db.js:187-192`) делает три запроса без транзакции. Если последний упадёт, подписки уже стёрты, а пользователь остался.

## Решения владельца (25.09.2026)

- Всё перечисленное переносится на сервер сразу, без промежуточных вариантов. Реальных пользователей нет.
- **Старые данные из браузеров не переносятся.** Сайт перестаёт их читать и один раз удаляет у себя из браузера (часть 7).
- **Фото хранятся на диске VPS**, в папке вне репозитория. Доступ к файлам только через один модуль-прослойку, чтобы потом можно было переехать на объектное хранилище, заменив один файл.
- **Не больше 5 фото на пункт чек-листа.**
- **Бесплатный профи: 1 расчёт в месяц.** Лимит проверяется на сервере. Снимает его только уровень `pro` (включая `pro_trial`). Подписка Клуба лимит не снимает: Клуб это B2C-контур.
- **Консультации:** прежнее правило, 3 в календарный месяц, но считает сервер.

## Решения, принятые в ТЗ по умолчанию (Дмитрий, поправь, если не так)

- Общий потолок на фото одного пользователя: **50 МБ**.
- Месяц для лимитов: **календарный, по московскому времени** (`Europe/Moscow`).
- **Результат B2B-квиза показывается только вошедшему пользователю.** Иначе лимит не посчитать. Если исполнитель обнаружит, что `/b2b-quiz` сейчас доступен без входа, на шаге «показать результат» незалогиненному открывается окно входа, после входа расчёт сохраняется и показывается. Анонимный B2C-квиз не трогается.
- Все числа (5 фото, 50 МБ, 1 расчёт, 3 консультации) живут константами в одном месте, `src/data/tariffs.js`, который уже импортирует и сервер (`PLANS`). В коде чисел не писать.

## Часть 1. Схема и удаление пользователя (`server/db.js`)

**1.1. Новые таблицы** в `initDB()` (после `subscriptions`, строки 38-49), через `CREATE TABLE IF NOT EXISTS`:

```sql
calculations (
  id           SERIAL PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind         VARCHAR(20) NOT NULL,      -- 'b2b' | 'office'
  project_name VARCHAR(255),
  data         JSONB NOT NULL,            -- answers/inputs + result, как сейчас в объекте calc
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS calculations_user_created ON calculations(user_id, created_at);

checklists (
  id           SERIAL PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  checklist_id VARCHAR(50) NOT NULL,
  state        JSONB NOT NULL,            -- { items, meta }, в photos вместо base64 id фото
  updated_at   TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE (user_id, checklist_id)
);

checklist_photos (
  id           SERIAL PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  checklist_id VARCHAR(50) NOT NULL,
  item_key     VARCHAR(20) NOT NULL,
  file_name    VARCHAR(100) NOT NULL,     -- случайное имя, не из запроса
  size_bytes   INTEGER NOT NULL,
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS checklist_photos_user ON checklist_photos(user_id);

consultations (
  id           SERIAL PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS consultations_user_created ON consultations(user_id, created_at);
```

Типы и имена можно уточнить, если при реализации найдётся причина; причину написать в отчёте.

**1.2. `deleteUser`** (строки 187-192) переписать в одну транзакцию на одном клиенте пула (`pool.connect()`, `BEGIN`, `COMMIT`, `ROLLBACK` в `catch`, `release` в `finally`). Внутри: удаление `subscriptions` и `auth_codes` как сейчас, затем `users`. Новые таблицы удаляются каскадом.

**Файлы фото удаляются после `COMMIT`**, вызовом прослойки из части 2 (`deleteUserFiles(userId)`). Если удаление файлов упало, писать в лог и не откатывать: лишние файлы на диске лучше, чем запись в базе, ссылающаяся на удалённого человека. Id пользователя для удаления файлов взять до транзакции.

**Не менять** внешний ключ `subscriptions.user_id` (без `ON DELETE`): ручное удаление в транзакции его покрывает, а переделка ограничения на боевой таблице в этой задаче не нужна.

## Часть 2. Хранилище файлов (`server/storage.js`, новый файл)

Единственное место, которое знает, что фото лежат на диске.

- Корень из переменной окружения `UPLOAD_DIR`. Значение в код не писать; если переменная не задана, сервер при старте пишет в лог предупреждение, а эндпоинты загрузки отвечают `503`.
- Раскладка: `UPLOAD_DIR/<user_id>/<случайное_имя>.jpg`. Имя генерировать на сервере (`crypto.randomUUID()`), никогда не брать из запроса.
- Функции: `savePhoto(userId, buffer) → fileName`, `photoPath(userId, fileName) → абсолютный путь`, `deletePhoto(userId, fileName)`, `deleteUserFiles(userId)` (удаляет папку пользователя целиком).
- `photoPath` проверяет, что итоговый путь лежит внутри `UPLOAD_DIR/<user_id>/` (защита от `../` в имени).

## Часть 3. Эндпоинты (`server.js`)

Общие правила для всех новых маршрутов:

- `requireDB`, `authMiddleware`, затем пользователь берётся из базы через `findUserByEmail(req.user.email)`, как в существующих обработчиках (например строка 154). **Не использовать `req.user.id` из токена напрямую:** у удалённого и заново зарегистрированного пользователя токен может ещё жить со старым id. Если пользователь не найден, `401`.
- Все запросы к данным фильтруются по `user_id` найденного пользователя. Чужой id в URL даёт `404`, не `403` (не подтверждаем, что запись существует).
- Глобальный `express.json()` (строка 37) не трогать. Для маршрутов с телом расчёта или чек-листа подключить свой парсер с лимитом `500kb` на уровне маршрута.
- Ответы в формате, который уже принят в проекте: `{ ok: true, ... }` / `{ ok: false, error }`.

**3.1. Расчёты**

- `GET /api/calcs`: свои расчёты, новые сверху.
- `POST /api/calcs` `{ kind, projectName, data }`. `kind` только `'b2b'` или `'office'`. `'office'` принимается только при уровне `pro` (повторяет гейт страницы `B2BOfficePage.jsx:147` на сервере). Для `'b2b'` без уровня `pro`: посчитать записи пользователя за текущий календарный месяц по Москве; если уже есть лимит, ответ `403 { ok:false, error:'limit' }`. Уровень определять через `getActiveSubscription` и `tierOf`, как в существующем коде подписок.
- `DELETE /api/calcs/:id`.

**3.2. Чек-листы**

Доступ: уровень `club` или `pro` (тот же смысл, что `hasClub` на фронте, `docs/TASK_checklists_gate.md`). Без подписки `403`. **Данные при истечении подписки не удалять**, после оплаты они должны вернуться (критерий 7 того ТЗ остаётся в силе).

- `GET /api/checklists`: список `{ checklistId, state, updatedAt }` для страницы списка (прогресс по каждому).
- `GET /api/checklists/:checklistId`.
- `PUT /api/checklists/:checklistId` `{ state }`: upsert. Перед записью проверить, что каждый id в `state.items[*].photos` принадлежит этому пользователю и этому чек-листу; чужие и несуществующие id выкинуть из сохраняемого состояния.
- `DELETE /api/checklists/:checklistId`: сброс чек-листа (сейчас это `localStorage.removeItem`, `ChecklistsPage.jsx:61`). Удаляет состояние, записи фото и файлы фото этого чек-листа.
- `POST /api/checklists/:checklistId/photos`: `multipart/form-data`, одно поле `photo`, одно поле `itemKey`, **одно фото на запрос**. Библиотека `multer` (новая зависимость, в `dependencies`), хранение в памяти, лимит файла **1 МБ** (ниже дефолтного лимита nginx 1 МБ, чтобы не получать `413` от nginx раньше, чем ответит сервер). Принимать только `image/jpeg` (клиент всегда отдаёт JPEG, `ChecklistDetailPage.jsx:41`). Проверки до сохранения: не больше 5 фото на `(checklistId, itemKey)`, общий объём фото пользователя не превысит 50 МБ. Ответ `{ ok:true, photo:{ id } }`.
- `GET /api/checklists/photos/:id`: отдаёт файл, только владельцу. Заголовок `Cache-Control: private`.
- `DELETE /api/checklists/photos/:id`: удаляет запись и файл. Если на фронте сейчас нет удаления фото, эндпоинт всё равно нужен для сброса чек-листа; кнопку удаления фото в интерфейсе не добавлять, если её нет.

**3.3. Консультации** (`POST /api/consultation`, строки 332-356)

- До отправки письма посчитать записи `consultations` пользователя за текущий календарный месяц по Москве. При лимите `403 { ok:false, error:'limit' }`.
- Запись в `consultations` вставлять **только после успешной отправки письма**.
- В ответе возвращать остаток: `{ ok:true, left }`.
- Новый `GET /api/consultation/status` → `{ ok:true, left }`.

## Критерии приёмки

**Удаление**
1. Профи делает расчёт, заполняет чек-лист с фото, записывается на консультацию. Админ удаляет аккаунт. В базе у этого `user_id` нет ни одной строки ни в одной таблице, папки `UPLOAD_DIR/<user_id>` нет.
2. Тот же email регистрируется заново: кабинет пуст, чек-листы пусты, остаток консультаций полный, триал снова доступен.

**Изоляция**
3. Два разных аккаунта по очереди в одном браузере: каждый видит только свои расчёты и чек-листы.
4. После выхода в той же вкладке страницы `/b2b-result`, `/b2b-office-result`, `/b2c-result`, `/b2c-result-detail` не показывают расчёт предыдущего пользователя.
5. Запрос чужого расчёта, чек-листа или фото по id (через `fetch` в консоли) даёт `404`.

**Лимиты**
6. Бесплатный профи: первый расчёт в месяце сохраняется и показывается, второй даёт пейволл, результат не показывается. Прямой `POST /api/calcs` второй раз даёт `403 limit`.
7. Профи на `pro_trial` или `pro_monthly`: лимита нет.
8. Шестое фото на пункт: кнопка скрыта; прямой запрос даёт отказ сервера.
9. Четвёртая консультация в месяце: отказ сервера; очистка браузера лимит не сбрасывает.

**Перенос**
10. Чек-лист, заполненный на MacAir, открывается с теми же отметками и фото на другом устройстве.
11. PDF-акт печатается с фото.
12. Отметки и фото сохраняются при быстром уходе со страницы сразу после изменения.
13. Истечение подписки закрывает чек-листы, возврат подписки возвращает их нетронутыми.
14. Офисный расчёт открывается из кабинета.

**Уборка и сборка**
15. После первого захода на сайт в `localStorage` нет ключей `rpkm-b2b-calcs`, `rpkm_checklist_*`, `rpkm_consult_*`.

## Деплой (выполняет Дмитрий, только по команде, после ревью всех частей)

Отличается от обычного, поэтому расписано заранее:

1. **Бэкап базы** до `git pull`.
2. Создать `UPLOAD_DIR` на сервере, владелец `deploy`, вне `/home/deploy/rpkm`, чтобы `git pull` его не касался. Прописать `UPLOAD_DIR` в `.env` самостоятельно.
3. **`npm install`** после `git pull`: появилась зависимость `multer`, а обычная команда деплоя делает только `npm run build`.
4. Сборка и `pm2 restart rpkm` как обычно. Таблицы создаст `initDB()` при старте.
5. Решить, как `UPLOAD_DIR` попадает в бэкапы. Сейчас бэкапится только база.
