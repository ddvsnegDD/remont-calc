# ТЗ: пробный доступ для профессионалов и честный ответ кнопки триала

Найдено при боевой проверке 24.09.2026. Дмитрий нажал «Попробовать 14 дней
бесплатно» на `/club` под профессиональным аккаунтом, ничего не произошло. Разбор
показал четыре разных дефекта в одном месте.

## Проблема

### 1. Профессионалу предлагают то, чего ему нельзя

`server.js`, строка 196: `if (user.role === 'b2b') return res.status(400).json({ ok: false, error: 'Триал только для физических лиц' })`.

Отказ по замыслу, логика триала не сломана. Сломан интерфейс: на `/club` кнопка
«Попробовать 14 дней бесплатно» стоит **дважды** (строки 154 и 191), карточка
«ВАШ АККАУНТ» прямым текстом советует «Активируйте триал», и на пейволле
детальной сметы (`B2CDetailPage.jsx`, строка 222) та же кнопка ведёт на `/club`.
Роль приходит с сервера в `user.role` (`server.js`, строка 159) и доступна как
`user.role` в `useAuth()`, то есть страница знает, кому показывает, и всё равно
показывает.

### 2. Отказ прилетает тостом внизу экрана на пять секунд

`ClubPage.jsx`, строка 344: `position: fixed; bottom: 24`, автоснятие через 5
секунд (строки 45–49). Кнопка при этом в первом экране. Человек нажимает, смотрит
на кнопку, там ничего не меняется, а объяснение появилось полутора экранами ниже
и пропало. Владелец сайта нашёл этот текст только с третьей попытки и по
подсказке, куда смотреть.

### 3. `createTrialSubscription` врёт при активной подписке

`server/db.js`, строки 122–124:

```js
const existing = await getActiveSubscription(userId);
if (existing) return existing;
```

Сервер получает непустой результат, отдаёт `ok: true`, клиент пишет «Триал на 14
дней активирован!». Ничего не создалось. Человек с оплаченным годом нажмёт и
решит, что получил две недели сверху.

### 4. Профессионалу предлагают не тот контур

`/club` продаёт клубную подписку за 99 ₽. Профессионалу нужен PRO с офисным
детальным калькулятором, и это другая страница и другая цена.

## Решение Дмитрия от 24.09.2026

Профессионалу **дать пробный доступ, а не отказ**. Новый план `pro_trial`,
уровень `pro`, **7 дней**. Срок короче клубных четырнадцати, потому что PRO стоит
2 900 ₽ против 99 ₽.

## Часть 1. План `pro_trial`

### 1.1. Тариф

`src/data/tariffs.js`, объект `PLANS`:

```js
pro_trial: { id: 'pro_trial', tier: 'pro', price: 0, days: 7, label: 'РПКМ PRO · пробные 7 дней' },
```

Проверено: `PLANS` нигде не перебирается циклом, обращения только по ключу
(`tariffs.js` строки 19 и 25, `server.js` строки 303–304, плюс точечные
`PLANS.club_monthly` и подобные). Новый ключ не добавит строку ни в одну таблицу
тарифов на сайте.

`tierOf('pro_trial')` вернёт `'pro'` автоматически, а `hasPro` в `auth.jsx`
(строка 98) считается как `tier === 'pro'`. Отдельной правки доступов не нужно.

### 1.2. Миграции БД не требуется

`subscriptions.plan` объявлен как `VARCHAR(50)` без ограничения на значения
(`server/db.js`, строка 41). Новый план вставится без изменения схемы. **Бэкап
перед этой задачей не нужен**, структура БД не меняется.

### 1.3. `createTrialSubscription` учитывает роль и перестаёт врать

`server/db.js`, строка 122. Сигнатура становится
`createTrialSubscription(userId, plan, days)`: какой план и на сколько дней —
решает вызывающий, а не сама функция.

**Почему так, а не по роли внутри.** Сроки и уровни живут в
`src/data/tariffs.js`. `server.js` уже импортирует оттуда `PLANS` и `tierOf`
(строка 8), а `server/db.js` не импортирует ничего из `src/` и не должен начать:
это слой доступа к БД. Пусть он вставляет то, что ему передали.

```js
export async function createTrialSubscription(userId, plan, days) {
  const existing = await getActiveSubscription(userId);
  if (existing) return { created: false, reason: 'active', subscription: existing };

  // Пробный доступ даётся один раз на аккаунт, независимо от плана: и клубный,
  // и профессиональный пишутся со status = 'trial'.
  const { rows: past } = await pool.query(
    `SELECT id FROM subscriptions WHERE user_id = $1 AND status = 'trial' LIMIT 1`,
    [userId]
  );
  if (past.length > 0) return { created: false, reason: 'used' };

  const expires = new Date(Date.now() + days * 24 * 60 * 60 * 1000);
  const { rows } = await pool.query(
    `INSERT INTO subscriptions (user_id, plan, status, expires_at) VALUES ($1, $2, 'trial', $3) RETURNING *`,
    [userId, plan, expires]
  );
  return { created: true, subscription: rows[0] };
}
```

В `server.js` план и срок собираются из тарифов, числами 14 и 7 в коде не
пишутся:

```js
const plan = user.role === 'b2b' ? 'pro_trial' : 'trial';
const result = await createTrialSubscription(user.id, plan, daysOf(plan));
```

`daysOf` придётся добавить в существующий импорт на строке 8.

Вызов один, `server.js` строка 197 — других нет, проверено грепом.

### 1.4. Эндпоинт

`server.js`, строки 193–204.

- Проверку роли **убрать**: отказа больше нет.
- Передавать `user.role` в `createTrialSubscription`.
- Разобрать три исхода:
  - `created: true` → `ok: true`, плюс в ответе `plan`, чтобы клиент мог сказать
    «PRO на 7 дней» или «Клуб на 14 дней», а не гадать.
  - `reason: 'active'` → `ok: false`, `error: 'У вас уже есть активная подписка'`.
  - `reason: 'used'` → `ok: false`, `error: 'Пробный доступ уже был использован'`.

## Часть 2. Ответ виден рядом с кнопкой

`src/pages/ClubPage.jsx`.

Тост внизу экрана оставить можно, но он не должен быть единственным каналом. Для
действия, меняющего доступ к платной функции, ответ обязан появляться там, куда
человек смотрит.

Что сделать: показывать результат прямо в блоке, где стоит нажатая кнопка —
строкой под ней. Успех и отказ различимы по виду. Без автоснятия через пять
секунд: сообщение живёт, пока человек не уйдёт со страницы или не нажмёт снова.

Тот же принцип для `handlePay` и `handleCancel` в этом же файле — они пользуются
тем же `notice` и страдают тем же.

## Часть 3. Кому что показывать

Роль известна из `user.role`. Дальше три состояния.

| кто | что видит вместо нынешнего |
|---|---|
| Физлицо без подписки | как сейчас: «Попробовать 14 дней бесплатно» |
| Профессионал без подписки и без использованного триала | «Попробовать PRO 7 дней бесплатно», та же кнопка, тот же эндпоинт |
| Профессионал, уже использовавший пробный доступ | кнопку не показывать, вместо неё ссылка «Оформить PRO — 2 900 ₽/мес» на `/pro` |

Карточка «ВАШ АККАУНТ» на `/club` для профессионала без подписки должна говорить
про PRO, а не «Активируйте триал или оформите подписку».

Пейволл на `/b2c-detail` (`B2CDetailPage.jsx`, строки 218–224) для профессионала
должен вести на `/pro`, а не на `/club`.

**Как узнать, был ли триал.** Сейчас клиент этого не знает: `/api/auth/me`
отдаёт только активную подписку. Добавить в ответ `me` поле `trialUsed`
(булево, тем же запросом, что уже проверяет `status = 'trial'`). Без него третье
состояние из таблицы не отличить от второго, и человек снова упрётся в отказ
после клика.

## Не трогать

- Правило «триал один раз на аккаунт». Оно остаётся, просто теперь покрывает оба
  плана через общий `status = 'trial'`.
- Цены и сроки платных планов.
- `grantSubscription` и админские ручки.
- Логику `hasClub`/`hasPro`/`hasAccess` в `auth.jsx`: новый план вписывается в
  неё сам через `tierOf`.
- Схему БД.

## Критерии приёмки

1. Профессиональный аккаунт без подписки на `/club` видит «Попробовать PRO 7 дней
   бесплатно». Нажатие создаёт подписку `pro_trial` на 7 дней, ответ появляется
   рядом с кнопкой, доступ к PRO-функциям открывается без перезахода.
2. Тот же аккаунт после окончания или повторного нажатия видит «Пробный доступ
   уже был использован» и ссылку на `/pro`, а не кнопку триала.
3. Физлицо без подписки: поведение прежнее, `trial` на 14 дней, уровень `club`.
4. Аккаунт с активной подпиской при нажатии получает «У вас уже есть активная
   подписка», а не «Триал активирован!».
5. Триал по-прежнему даётся один раз: физлицо, взявшее клубный триал, не может
   потом взять профессиональный, и наоборот.
6. `tierOf('pro_trial')` возвращает `'pro'`, `daysOf('pro_trial')` возвращает 7.
7. Таблицы тарифов на `/club`, `/pro` и главной не изменились: нового плана в них
   не появилось.
8. Пейволл детальной сметы для профессионала ведёт на `/pro`.
9. `node --check server.js` и `node --check server/db.js` проходят.
10. `npx vite build` проходит без ошибок.
11. Отчёт `docs/REPORT_trial_b2b.md` написан по фактическим результатам.

## Порядок работ

1. Часть 1 — сервер и тариф. Отдельным коммитом, потому что это единственная
   часть, которая трогает бэкенд и БД-запросы.
2. Часть 3 — `trialUsed` в `/api/auth/me` и интерфейс по ролям.
3. Часть 2 — вывод ответа рядом с кнопкой.

Проверять придётся на боевом: локально нет БД. Поэтому деплой этой задачи
делается по отдельной команде, и критерии 1–5 закрываются после него, под двумя
аккаунтами — профессиональным и физлицом.
