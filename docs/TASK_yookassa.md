**Дата:** 27.09.2026
**Делает:** Claude Code. Одна часть — один коммит, без push, после каждой части стоп и короткий отчёт.
**Режим:** разработка и боевая проверка — в **тестовом магазине ЮKassa** (ShopID 1380535). Переключение на настоящий магазин — отдельным шагом позже (после бэкапов и модерации магазина ddrpkm.ru), только заменой переменных окружения, без правки кода.

## Проблема

Контур ЮMoney вырезан 18.09.2026. С тех пор кнопки «Оплатить» на `/club` и «Оформить PRO» на `/pro` показывают «Оплата временно недоступна» (`ClubPage.jsx:100`, `ProPage.jsx:42`). Купить подписку нельзя, доступ выдаётся только вручную через админку.

## Решения владельца

От 24.09.2026 (roadmap, раздел 4):
- Чеки **не автоматизируем**: владелец пробивает их вручную в «Мой налог». Сайт на каждую успешную оплату шлёт владельцу письмо со всем, что нужно для чека.
- **Автоплатежей нет.** Каждая оплата — разовая за период. Способ оплаты не сохраняем.
- Письмо-напоминание об окончании подписки — отдельная задача, в это ТЗ не входит.

От 27.09.2026:
1. **Продление с конца текущего доступа.** Если у человека идёт подписка или триал, оплаченный период начинается с момента, когда закончится текущий. Ничего не сгорает.
2. **Клуб → PRO: PRO сразу, Клуб сгорает.** Покупка PRO при активном Клубе (включая клубный триал) начинает PRO с момента оплаты на 30 дней; клубный доступ закрывается. Покупка PRO при активном PRO или PRO-триале — по п. 1, в хвост.
3. **Кнопку «Отменить подписку» убрать.** Подписка просто заканчивается в срок. Возврат — по письму, владелец делает его в кабинете ЮKassa; сайт по уведомлению о возврате сам закрывает доступ, купленный этим платежом.
4. **Только физлица.** Оплата картой/СБП на сайте. Юрлица и ИП — отдельная задача позже.

## Решения по умолчанию (Дмитрий, поправь, если не так)

- Покупка Клуба при активном PRO — по п. 1: Клуб встаёт в очередь после окончания PRO.
- Сумма и план берутся **только с сервера** (`PLANS` в `src/data/tariffs.js`). Клиент присылает только id плана.
- Записи о платежах при удалении аккаунта **не удаляются, а обезличиваются**: `user_id` → NULL, остаются сумма, дата, id платежа ЮKassa, статус. Причина — возвраты и сверка с «Мой налог» после удаления аккаунта. Email в таблицу платежей не пишется. В политике это будет сказано явно (часть 4).

## Часть 1. База данных (`server/db.js`)

### 1.1. Таблица `payments`

```
CREATE TABLE IF NOT EXISTS payments (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
  plan VARCHAR(50) NOT NULL,
  amount INTEGER NOT NULL,              -- в рублях, из PLANS на момент создания
  yookassa_id VARCHAR(64) UNIQUE,       -- id платежа в ЮKassa
  status VARCHAR(32) NOT NULL DEFAULT 'pending',  -- pending | succeeded | canceled | refunded
  subscription_id INTEGER REFERENCES subscriptions(id) ON DELETE SET NULL,
  applied_at TIMESTAMPTZ,               -- когда выдан доступ; NOT NULL = платёж уже применён
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

Индекс по `user_id`. Таблица создаётся в `initDB()` так же, как таблицы из TASK_server_storage.

### 1.2. Будущий старт подписки

Сейчас `getActiveSubscription` (`server/db.js:155`) не учитывает `started_at`. Для очереди (п. 1 решений) подписка может начинаться в будущем. Изменить условие: `started_at <= NOW() AND expires_at > NOW()`. Проверить **все** места, где читается подписка (`grep -n "subscriptions" server/db.js server.js`), на то же допущение — в отчёте перечислить.

### 1.3. `applySucceededPayment(paymentId)` — выдача доступа

Одна транзакция, `SELECT ... FOR UPDATE` строки `payments`. Если `applied_at` уже не NULL — ничего не делать и вернуть существующую подписку (**идемпотентность**: ЮKassa повторяет уведомления, плюс проверка при возврате пользователя — см. часть 2; двойная выдача недопустима).

Логика:
- `tier = tierOf(plan)`, `days = daysOf(plan)` — числа только из `tariffs.js`. `db.js` не импортирует `src/` (так заведено, `db.js:163–167`), поэтому tier и days передаёт вызывающий из `server.js`.
- Активные подписки пользователя: `status IN ('trial','active') AND expires_at > NOW()`, включая будущие.
- **Покупка PRO:** клубные (tier club, включая legacy и `trial`) закрыть: `status='cancelled', expires_at=NOW()` для текущих, `status='cancelled'` для будущих. Старт = максимум `expires_at` среди оставшихся PRO-подписок, иначе `NOW()`.
- **Покупка Клуба:** старт = максимум `expires_at` среди всех активных и будущих, иначе `NOW()`.
- Вставить `subscriptions(user_id, plan, status='active', started_at=старт, expires_at=старт + days, payment_id=yookassa_id, amount)`.
- В `payments`: `status='succeeded', subscription_id, applied_at=NOW(), updated_at=NOW()`.

### 1.4. `applyRefund(yookassaPaymentId)`

Найти платёж. Если связанная подписка ещё не истекла — `status='refunded', expires_at=LEAST(expires_at, NOW())`; если она в будущем — `status='refunded'`. Платёж → `status='refunded'`. Идемпотентно. Подписки, стоящие в очереди **после** возвращённой, не сдвигать (редкий случай, владелец поправит руками) — в отчёте отметить.

### 1.5. Удаление пользователя

`deleteUser` удаляет подписки явно (`db.js:235`). Перед этим обнулить `payments.subscription_id` и `payments.user_id` для этого пользователя (FK `ON DELETE SET NULL` сработает и сам, но порядок удаления подписок должен не упасть на FK `subscription_id`). Проверить, что удаление аккаунта с платежами проходит.

### 1.6. `grantSubscription` (админка)

Сейчас закрывает `trial/active/pending`. Добавить закрытие будущих (они тоже `active`). Поведение «выдал руками — всё прежнее закрыто» сохраняется.

Критерии части 1: `node --check server/db.js`; разбор каждой ветки п. 1.3 на примерах в отчёте (Клуб-триал до 10.10 + покупка Клуба 27.09 → до 09.11; Клуб до 10.10 + PRO 27.09 → PRO 27.09–27.10, Клуб закрыт; PRO-триал до 03.10 + PRO → 03.10–02.11; повторное применение того же платежа → без изменений).

## Часть 2. Сервер (`server.js`, новый `server/yookassa.js`)

### 2.1. `server/yookassa.js`

Тонкий клиент API ЮKassa v3 (`https://api.yookassa.ru/v3`) на встроенном `fetch`, без новых зависимостей:
- переменные окружения `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`; если нет — `isPaymentsReady() === false`, в лог предупреждение при старте, эндпоинты оплаты отвечают `503 {error:'payments_off'}`, сайт работает;
- Basic-авторизация `shopId:secretKey`, заголовок `Idempotence-Key` (uuid) на создание;
- `createPayment({amount, description, returnUrl, metadata})` → `POST /payments` с `capture: true`, `confirmation: {type:'redirect', return_url}`, `amount.value` строкой с копейками (`"99.00"`), `currency: 'RUB'`;
- `getPayment(id)`, `getRefund(id)`;
- таймаут запроса (AbortController, 10 с), ответы не-2xx → понятная ошибка в лог **без ключа и без заголовка Authorization**.

Секретный ключ в код, логи, ответы и в `.env.example` значением не попадает. В `.env.example` — только имена двух переменных с пояснением.

Если ЮKassa потребует передать чек (`receipt`) при создании платежа (ошибка про 54-ФЗ) — **остановиться и доложить**, не придумывать чек.

### 2.2. `POST /api/payments/create`

`requireDB, authMiddleware`. Тело: `{plan}`. Разрешены только `club_monthly`, `club_yearly`, `pro_monthly` (не триалы). Пользователь через `findUserByEmail` (как везде). Лимит: не больше 10 созданий в 10 минут на пользователя (существующий `rateLimit`).

1. Вставить `payments(user_id, plan, amount=PLANS[plan].price, status='pending')`.
2. `createPayment`: сумма из `PLANS`, `description` — «РПКМ: <labelOf(plan)>», `metadata: {payment_row_id, user_id, plan}`, `return_url` = `${APP_URL}/payment/return?p=<payments.id>`.
3. Сохранить `yookassa_id`. Ответ `{ok:true, confirmationUrl}`.

Ошибка ЮKassa → строка остаётся `pending` без `yookassa_id`, ответ `502 {error:'provider'}`.

### 2.3. `POST /api/payments/yookassa/webhook`

Без авторизации (её шлёт ЮKassa). Телу уведомления **не доверять**: взять из него только `event` и `object.id`, затем запросить объект заново через API (`getPayment` / `getRefund`) и действовать по ответу API. Это защита от подделанных уведомлений.

- `payment.succeeded` → по `getPayment(id)`: статус `succeeded`, `paid === true`, сумма и валюта совпадают со строкой `payments` (найденной по `yookassa_id`) → `applySucceededPayment`, затем письмо владельцу (п. 2.5).
- `payment.canceled` → `payments.status='canceled'`.
- `refund.succeeded` → `getRefund(id)` → `payment_id` → `applyRefund` (исправлено: любой возврат закрывает доступ); частичный — дополнительно письмо владельцу «частичный возврат, доступ по этой оплате закрыт».
- Неизвестные события и платежи, которых нет в `payments`, — ответ 200 и запись в лог.

Отвечать **200** на всё, что обработано или сознательно пропущено; **500** — только при сбое БД или API, чтобы ЮKassa повторила. Проверить, что маршрут принимает JSON при глобальном `express.json()` (`server.js:52`).

### 2.4. `GET /api/payments/:id`

`authMiddleware`, только свой платёж (чужой → 404, как в TASK_server_storage). Если строка ещё `pending` и есть `yookassa_id` — спросить ЮKassa (`getPayment`) и при `succeeded` применить тем же `applySucceededPayment` (второй путь на случай, если уведомление запаздывает). Ответ: `{ok, status, plan, subscription: {plan, expiresAt, startsAt}}`.

### 2.5. Письмо владельцу об оплате

На каждое **первое** применение успешного платежа (не на повтор) — письмо на `CONTACT_EMAIL` (или текущий адрес владельца, как в письмах о консультации): «Оплата: <labelOf(plan)>, <сумма> ₽», дата и время по Москве, email покупателя, id платежа ЮKassa, период доступа. Пометка «Выдайте чек в „Мой налог“». Все пользовательские значения через `escapeHtml`. В тестовом магазине в теме письма — «[ТЕСТ]» (признак тестового режима из ответа ЮKassa: `test: true`).

### 2.6. Отмена подписки пользователем

Удалить `POST /api/subscription/cancel` (`server.js:292`) и `cancelSubscription`, если больше нигде не используется (`grep`). Отзыв подписки в админке не трогать.

Критерии части 2: `node --check` для `server.js` и `server/yookassa.js`; в отчёте — как проверено без настоящих ключей (заглушка `fetch`, ручной вызов обработчиков), и что осталось проверить на тестовом магазине.

## Критерии приёмки (боевая проверка на тестовом магазине)

1. Физлицо без подписки покупает «Клуб · 1 месяц» тестовой картой → попадает на страницу ЮKassa → после оплаты `/payment/return` показывает «Оплата прошла, до <сегодня + 30>», в Клубе доступ есть.
2. Та же покупка при активном клубном триале → срок добавлен к концу триала.
3. Клуб → PRO: PRO с сегодняшнего дня на 30 дней, Клуб закрыт, PRO-функции доступны.
4. Отмена на странице ЮKassa (или отклонённая тестовая карта) → «Оплата не прошла», подписка не появилась.
5. Повтор уведомления (кнопка повторной отправки в кабинете ЮKassa или повторный запрос) → вторая подписка **не** появляется.
6. Полный возврат из кабинета ЮKassa → доступ по этому платежу закрыт.
7. Владельцу приходит письмо «[ТЕСТ] Оплата…» с данными для чека; на повторе — не приходит.
8. Чужой `GET /api/payments/<id>` → 404.
9. Удаление аккаунта с платежами проходит; строки `payments` остались с `user_id = NULL`.
10. Без `YOOKASSA_*` в `.env` сайт работает, кнопки оплаты показывают понятное сообщение.
11. Кнопки «Отменить подписку» нет.
12. `node --check`, `npx vite build` проходят.
