## Три расхождения с ТЗ, зафиксированные по вашему указанию

### 1. Часть 2: `useAuth()` на строке 382 — не в `ProSection`

ТЗ утверждало: «`useAuth()` вызывается один раз, в `ProSection` (строка 382)». Фактически на строке 382 `useAuth()` вызывается внутри `ContactSection`, а не `ProSection`; грепом по файлу подтверждено — вызов `useAuth()` в файле ровно один, и он принадлежит `ContactSection`. В `ProSection` вызова `useAuth()` не было вовсе. Ошибка автора ТЗ. `ContactSection` не трогалась; в `ProSection` добавлен собственный, новый вызов `useAuth()`.

### 2. Часть 3.2: логика «уровень из результата квиза» для B2B уже существовала

ТЗ описывало проблему как «начальное значение задано жёстко и не зависит от того, что выбрано в квизе», и предлагало взять уровень из `calc.answers.repair_type`. Фактически:
- у B2B-квиза поля `repair_type` в принципе нет (это поле только у B2C-квиза; `calculateB2B` строит tier из `wall_finish`/`floor_finish`/`ceiling_finish`/`engineering`, не из `repair_type`) — буквальная реализация инструкции всегда давала бы фолбэк `'capital'`, то есть не решала бы описанную проблему вообще;
- логика «взять уровень из результата квиза» в `B2BResultPage.jsx` **уже существовала** — `useEffect` уже вызывал `setSpecTier(tierMap[c.result?.tier] || 'capital')` до этой правки (добавлено коммитом `42728c4`, задолго до этого ТЗ).

Ошибка автора ТЗ дважды: неверное имя поля-источника и не замеченное существующее решение. Фактическая ценность правки 3.2 — не новое поведение, а устранение разошедшегося дубля `tierMap` (четыре ключа в версии B2C против шести в версии B2B, два независимых места правки на будущее) сведением в один модуль `src/data/specTier.js`. Само поведение (страница открывается на уровне, вычисленном из квиза) не изменилось — оно и раньше корректно резолвилось в `'premium'` для типового B2B-расчёта, что и подтверждено прогоном выше.

### 3. Находка, не входящая в это ТЗ: `calculateB2B` не даёт выбора уровня отделки

`calculator.js:218-224`:
```js
let tier = 'premium';
let luxScore = 0;
if (answers.wall_finish === 'stone') luxScore++;
if (answers.floor_finish === 'marble') luxScore++;
if (answers.ceiling_finish === 'molding') luxScore++;
if (answers.engineering === 'special') luxScore++;
if (luxScore >= 3) tier = 'luxury';
```
B2B-квиз не даёт пользователю выбрать уровень отделки вообще — `tier` всегда `'premium'`, и только при трёх и более признаках роскоши (камень, мрамор, лепнина, спецсистемы одновременно) становится `'luxury'`. Значения `'cosmetic'`, `'capital'`, `'euro'` для B2B-расчёта в принципе недостижимы.

Следствие: `B2BResultPage.jsx`'s `specTier` через `toSpecTier` всегда резолвится в `'premium'` — детальная спецификация в B2B **всегда** открывается на премиальном наборе позиций, независимо от того, что человек реально выбрал по отделке стен/потолков/полов в квизе.

Ваши цифры: премиальная детальная смета — **423 317 ₽/м²** (это значение независимо перепроверено скриптом через `SpecCalc.compute` с `tier: 'premium'` — совпадает точно), против премиальной вилки быстрого квиза **191 788 – 263 708 ₽/м²**. Разрыв больше, чем просто «квиз занижает» (см. аналогичный, но отдельный разрыв в `calc_input_hardening`, там же +39% для B2C) — здесь у B2B-пользователя физически нет пути получить в детальной смете что-то, кроме премиального набора позиций, даже если в квизе он выбрал скромную отделку.

В коде по этому пункту ничего не менялось — это предмет отдельной задачи, по масштабу похожей на `TASK_spec_tiers.md`, только для B2B-ветки.
