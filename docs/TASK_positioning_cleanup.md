## 0. Контекст и цель

Сайт исторически сделан как воронка лидогенерации для ремонтной компании: обещает выезд инженера
на бесплатный замер, фиксированную цену в договоре, гарантию на работы, личного куратора,
процент от чека партнёрам. Ничего из этого владелец сайта не оказывает — он не ремонтная компания.

**Цель:** привести интерфейс и тексты в соответствие с реальным продуктом — онлайн-калькулятором
стоимости отделки с монетизацией через подписку. Всё, что обещает выполнение ремонтных работ,
выезд специалиста, договор подряда, гарантию на работы и выплаты за приведённых заказчиков,
должно быть удалено или переписано.

**Что НЕ трогаем в этой задаче:**
- расчётную логику (`src/lib/calculator.js`, `spec-calculator.js`, `office-calculator.js`, `src/data/*`);
- авторизацию, подписки, платежи ЮMoney, админку;
- Клуб владельцев, чек-листы, PRO-кабинет как продукты (только тексты внутри, если они обещают ремонт).

---

## 1. Правила выполнения

1. Работать по этапам. **Каждый этап — отдельный коммит** с понятным сообщением.
   Не смешивать этапы в одном коммите.
2. После каждого этапа: `npm run build` — сборка должна проходить без ошибок и без новых warning'ов
   о неиспользуемых импортах.
3. При удалении компонента/страницы обязательно удалить: импорт, роут, все ссылки на него,
   и — если после этого CSS-класс больше нигде не используется — сам класс из `src/styles/global.css`.
   Перед удалением класса проверять `grep -rn "имя-класса" src/`. Если класс используется где-то ещё — не трогать.
4. Не удалять файлы изображений из `public/images/` в рамках этапов 1–3. По завершении всех этапов
   отдельно составить список изображений, на которые не осталось ни одной ссылки, и показать его —
   удалять только после подтверждения.
5. Тексты писать в существующей стилистике сайта: короткие фразы, без восклицаний, «вы» со строчной.
6. Если по ходу работы находится место с подрядческим обещанием, **не описанное в этом ТЗ**, —
   не додумывать формулировку: внести в раздел «Найдено дополнительно» в конце отчёта и спросить.

#### 2.9.1. Серверный эндпоинт

В `server.js` добавить `POST /api/calculation`. Отправка — через существующую
`sendRawEmail(to, subject, html)`.

```
POST /api/calculation
Body: { email, name, kind: 'quick' | 'detail', result }
Ответ: { ok: true } | { ok: false, error: "..." }
```

Требования:

1. **Письмо формируется сервером из известных числовых полей `result`, а не из произвольного
   текста клиента.** Никакой пользовательский HTML в письмо не попадает. `name` перед вставкой
   экранировать (`& < > " '`). Это не паранойя: эндпоинт отправляет письма на любой указанный
   адрес, и без такого ограничения он превращается в открытый релей для рассылки чего угодно
   от вашего домена — с последствиями для репутации домена и доставляемости.
2. Валидация: `email` по regex, `name` 2–100 символов, `kind` — только одно из двух значений,
   `result` — объект. Иначе `400`.
3. Rate limit: не более **5 писем с одного IP за 15 минут**, in-memory `Map` по `req.ip`.
   При превышении — `429`.
   *Тот же механизм понадобится в Этапе 4 для `/api/contact` — имеет смысл сразу написать
   маленькую переиспользуемую функцию `rateLimit(key, max, windowMs)` и применить её в обоих местах.*
4. Ошибку отправки логировать, пользователю возвращать `{ ok: false }` — но **навигацию на
   странице результата это блокировать не должно** (см. 2.9.2).

Содержимое письма:

- Тема: `РПКМ · Ваш расчёт стоимости отделки`
- Для `kind: 'quick'` — площадь, категория, вилка стоимости, цена за м², разбивка на работы /
  черновые / чистовые материалы с процентами, ориентировочные сроки.
- Для `kind: 'detail'` — площадь, режим, итоговая сумма, цена за м², доли работ и материалов,
  количество позиций в смете. Полную таблицу в письмо **не тащить** — вместо неё ссылка на сайт.
- В конце письма — дисклеймер: `Расчёт носит предварительный характер: итоговая стоимость
  зависит от конкретных материалов, объёмов по факту и условий подрядчика.`
- Ссылка на `https://ddrpkm.ru`.

### 4.4. Серверный эндпоинт

В `server.js` добавить `POST /api/contact`. Отправку письма делать через **уже существующую**
функцию `sendRawEmail(to, subject, html)` из `./server/email.js` (она уже импортирована в `server.js`),
провайдер — тот же, что для кодов авторизации (UniSender Go).

```
POST /api/contact
Body: { name, email, message, website }
Ответ: { ok: true } | { ok: false, error: "..." }
```

Логика:
1. Если `website` непустое — вернуть `{ ok: true }` и **ничего не отправлять** (бот).
2. Валидация на сервере, повторяющая фронтендовую (нельзя полагаться на клиент):
   `name` 2–100 символов, `email` по regex, `message` 10–2000 символов.
   При провале — `400` и `{ ok: false, error: 'Проверьте заполнение полей' }`.
3. Rate limit: не более **3 сообщений с одного IP за 15 минут**. Отдельного middleware
   в проекте нет — сделать простой in-memory `Map` (ключ — IP из `req.ip`, значение — массив
   таймстампов), с очисткой старых записей при каждом обращении. При превышении — `429`
   и `{ ok: false, error: 'Слишком много сообщений. Попробуйте позже.' }`.
4. Экранировать пользовательский ввод перед вставкой в HTML письма (простая функция
   замены `& < > " '`) — иначе получаем XSS в собственной почте.
5. Отправить письмо:
   - получатель: `process.env.CONTACT_EMAIL || 'ddv1121@yandex.ru'`;
   - тема: `РПКМ · Сообщение с сайта от {name}`;
   - тело: имя, email, дата/время (МСК), IP, затем текст сообщения с сохранением переносов строк
     (`\n` → `<br>`);
   - **`Reply-To` поставить в email отправителя**, чтобы можно было ответить прямо из почты.
     Текущая сигнатура `sendRawEmail(to, subject, html)` этого не поддерживает — либо расширить её
     необязательным четвёртым параметром `replyTo` (аккуратно, функция используется и в других местах),
     либо, если это тянет за собой правки во всех провайдерах, продублировать email отправителя
     первой строкой письма крупно. **Предпочтительно — расширить `sendRawEmail`.**
6. Ошибку отправки логировать в консоль (`console.error`), пользователю возвращать
   `{ ok: false, error: 'Не удалось отправить сообщение. Напишите на ddv1121@yandex.ru' }`.
7. В `.env.example` / `README.md` добавить `CONTACT_EMAIL`.

Сообщения **в базу не пишем** — по решению от 03.09.2026 достаточно письма.

детальная спецификация B2B по тендерным ценам, приоритетная поддержка, и всё, что входит
в Клуб. Формулировку согласовать с Дмитрием до внесения.

### 5.2. Объём консультаций расходится с сайтом

Оферта, п. 2.1: «Консультацию со специалистом по ремонту» — единственное число, без периодичности.
Сайт: «Консультации инженера — до 3 вопросов в месяц».

Продаём больше, чем обязуемся. Привести оферту к тому, что обещает сайт: указать количество
и период, а также правило накопления (на `ClubPage` сказано «можно копить — до 9 консультаций»).

### 5.3. «Специалист по ремонту»

П. 2.1 — единственная формулировка в оферте, которую можно прочитать как обязательство
предоставить подрядчика. Заменить на описание того, что реально оказывается: консультация
по расчёту и смете. Точную формулировку даёт Дмитрий.

### 5.4. Условие о возврате (вне рамок позиционирования)

П. 6.1 ограничивает возврат тремя днями и условием «Услугами фактически не воспользовался».
Ст. 32 Закона о защите прав потребителей даёт право отказаться от исполнения договора в любое
время с оплатой фактически понесённых исполнителем расходов; условие, ухудшающее положение
потребителя по сравнению с законом, ничтожно.

К развороту позиционирования отношения не имеет, но раз документ читается целиком — привести
в соответствие. Это тот пункт, где консультация юриста окупается.

### 5.5. Дата редакции

При любой правке оферты обновить дату публикации (сейчас 26 июля 2026 г.).

**Коммит для 5.1–5.5:** `docs(legal): привести оферту в соответствие с составом услуг`
