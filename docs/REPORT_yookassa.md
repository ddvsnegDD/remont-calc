## Часть 1. База данных (`server/db.js`)

### 1.1. Таблица `payments`

Создаётся в [`initDB()`](../server/db.js) вместе с индексом `payments_user_id`. Схема — точно
по п. 1.1 ТЗ: `user_id` с `ON DELETE SET NULL`, `status` (`pending|succeeded|canceled|refunded|orphaned`
— пятое значение добавлено в части 2, см. ниже), `applied_at` как признак идемпотентности.

### 1.2. Будущий старт подписки

[`getActiveSubscription`](../server/db.js:184) — условие `started_at <= NOW() AND expires_at > NOW()`
(было только `expires_at > NOW()`). Аудит всех мест, где читаются подписки
(`grep -n "subscriptions" server/db.js server.js`):

- [`getActiveSubscription`](../server/db.js:187) — поправлено (см. выше).
- [`applySucceededPayment`](../server/db.js:352) — **намеренно без** `started_at <= NOW()`: здесь
  нужна вся очередь (текущее и уже поставленное в очередь), не только действующее сейчас.
- [`getAdminStats`](../server/db.js:739), `active_paid` — поправлено тем же условием.
- [`getAdminStats`](../server/db.js:734), `active_trials` — оставлено без `started_at`: триалы
  никогда не встают в очередь (создаются с `started_at = NOW()` в момент активации), проверка
  избыточна, но безвредна.
- [`grantSubscription`](../server/db.js:232) — закрывающий `UPDATE` без `started_at` вообще
  (см. п. 1.6 ниже — это осознанно).
- [`cancelSubscription`](../server/db.js:262) — тот же пробел, что был у `getActiveSubscription`
  до правки; не тронут (см. часть 2.6 ниже — функция используется только админкой, риск трогать
  вне заявленной части выше пользы).

### 1.3. `applySucceededPayment(paymentId, tier, days)`

[`server/db.js:306`](../server/db.js:306). Идемпотентность — `SELECT ... FOR UPDATE` строки
`payments`, ранний `COMMIT` с `{applied:false, subscription}`, если `applied_at` уже стоит.

Разбор веток на примерах из критериев части 1 (сегодня считаем 27.09.2026):

1. **Клуб-триал до 10.10 + покупка Клуба 27.09.** `tier='club'`, `existing` содержит триал с
   `expires_at = 10.10`. Ветка `else` ([`db.js:379`](../server/db.js:379)): `start = max(expires_at
   среди existing) = 10.10`. Новая подписка `started_at=10.10, expires_at=09.11` (30 дней). Триал
   не трогается (не клубный конфликт, а просто предыдущий в очереди того же уровня) — итог:
   **до 09.11**, что и требуется.
2. **Клуб до 10.10 + PRO 27.09.** `tier='pro'`, `clubIds=[тот клуб]`, `proRows=[]`. Клубная
   подписка с `started_at <= NOW()` (уже действует) закрывается прямо сейчас:
   `status='cancelled', expires_at=NOW()=27.09` ([`db.js:365-369`](../server/db.js:365)).
   `proRows` пуст → `start=NOW()=27.09`. Новая PRO-подписка `27.09–27.10`. Итог: **PRO
   27.09–27.10, Клуб закрыт** — совпадает.
3. **PRO-триал до 03.10 + PRO.** `tier='pro'`, `clubIds=[]` (триал уже PRO-уровня — `PLAN_TIER`
   относит `pro_trial` к `'pro'`), `proRows=[триал]`. `start = max(expires_at) = 03.10`. Новая
   подписка `03.10–02.11`. Итог: **03.10–02.11** — совпадает.
4. **Повторное применение того же платежа.** Второй вызов видит `payment.applied_at` уже
   заполненным ([`db.js:314`](../server/db.js:314)) → ранний `COMMIT`, `{applied:false, ...}`,
   никаких новых строк `subscriptions`/изменений `payments`. Вторая подписка **не** появляется.

### Правка ревью части 1 — сериализация по пользователю

Гонка: если активных подписок ещё нет вовсе, `SELECT ... FOR UPDATE` по `subscriptions`
([`db.js:352`](../server/db.js:352)) не блокирует ничего (нечего блокировать) — два одновременных
платежа одного пользователя оба увидели бы пустой `existing` и оба посчитали бы `start = NOW()`,
перекрыв друг друга. Добавлен `SELECT id FROM users WHERE id = $1 FOR UPDATE`
([`db.js:343`](../server/db.js:343)) сразу после проверки `payment.user_id` — строка `users`
существует всегда (пока аккаунт не удалён), поэтому блокировка на ней гарантированно
сериализует конкурентные транзакции: вторая ждёт первую до её `COMMIT`, и только потом читает
`existing`, к этому моменту уже видя вставленную первой подписку.

### 1.4. `applyRefund(yookassaPaymentId)`

[`server/db.js:411`](../server/db.js:411). Идемпотентно (`status==='refunded'` → ранний возврат
`{alreadyRefunded:true, payment}`). Подписки в очереди после возвращённой не сдвигаются
(осознанно, редкий случай — при заявленной модели «одна оплата — один период» покупка нового
периода поверх ещё не наступившего почти никогда не происходит; если случится — владелец
поправит вручную).

### 1.5. Удаление пользователя

[`deleteUser`](../server/db.js:508) обнуляет `payments.subscription_id` и `payments.user_id`
до удаления подписок (порядок важен: FK `subscription_id` не должен упасть на ещё существующие
строки `subscriptions`). Строки `payments` не удаляются, email в них не пишется изначально.

### 1.6. `grantSubscription` (админка)

[`server/db.js:232`](../server/db.js:232) — закрывающий `UPDATE` без фильтра по времени вообще,
значит будущие (`started_at > NOW()`) `active`-подписки тоже закрываются. Поведение «выдал руками
— всё прежнее закрыто» сохранено без изменений кода (условие и раньше не проверяло `started_at`).

## Часть 2. Сервер (`server.js`, `server/yookassa.js`)

### 2.1. `server/yookassa.js`

Тонкий клиент API ЮKassa v3: [`createPayment`](../server/yookassa.js:59),
[`getPayment`](../server/yookassa.js:89), [`getRefund`](../server/yookassa.js:93),
[`isPaymentsReady`](../server/yookassa.js:16). Basic-авторизация, `Idempotence-Key` (uuid) на
создание, таймаут 10 с (`AbortController`), ошибки логируются без ключа/заголовков
(`console.error` печатает только метод/путь/статус/тело ответа ЮKassa).

**Правка ревью (после части 2):** `getPayment`/`getRefund` проверяют id по
`/^[A-Za-z0-9-]{1,64}$/` ([`yookassa.js:76`](../server/yookassa.js:76)) и подставляют через
`encodeURIComponent`, а не голой интерполяцией; `isValidPaymentId`
([`yookassa.js:85`](../server/yookassa.js:85)) — та же проверка для вызывающего кода. В
вебхуке ([`server.js:420`](../server.js:420)) невалидный `object.id` отвечает 200 без похода
в API вовсе.

### 2.2. `POST /api/payments/create`

[`server.js:380`](../server.js:380). Тело `{plan}`, только `PAYABLE_PLANS`
([`server.js:307`](../server.js:307)) — без триалов. Лимит 10/10 мин на пользователя. Сумма и
план — только из `PLANS`; клиент не может подменить цену. Ошибка ЮKassa при создании → строка
`payments` остаётся `pending` без `yookassa_id`, ответ `502 {error:'provider'}`.

### 2.3. `POST /api/payments/yookassa/webhook`

[`server.js:419`](../server.js:419). Телу не доверяем — только `event` и `object.id`, дальше
`getPayment`/`getRefund` и действие по ответу API.

- `payment.succeeded` ([`server.js:427`](../server.js:427)) — проверка статуса/`paid`/суммы и
  валюты, затем `applySucceededPayment`; при `err.code==='PAYMENT_ORPHANED'` — письмо владельцу
  и `200` (см. ниже); прочие ошибки — `500`, ЮKassa повторит.
- `payment.canceled` ([`server.js:455`](../server.js:455)) — `payments.status='canceled'`.
- `refund.succeeded` ([`server.js:463`](../server.js:463)) — **исправлено после первичной сдачи
  части 2** (см. отдельный раздел ниже): любой успешный возврат закрывает доступ.
- Неизвестные события / платёж не найден в `payments` — `200` + лог.

### Доп. к 2.3/2.5 — платёж без аккаунта («orphaned»)

Если аккаунт удалён между созданием платежа и приходом успеха, `applySucceededPayment` бросает
ошибку с `err.code === 'PAYMENT_ORPHANED'` ([`db.js:289`](../server/db.js:289),
[`db.js:328`](../server/db.js:328), [`db.js:349`](../server/db.js:349) — второе место ловит тот
же случай на шаг позже, если аккаунт удалился между чтением `user_id` и блокировкой строки
`users`). Вебхук ловит это по `err.code` (не по тексту сообщения), шлёт владельцу письмо «Оплата
без аккаунта: нужен возврат» ([`sendOrphanedPaymentEmail`](../server.js:344): сумма, план, id
платежа ЮKassa, время по Москве) и отвечает ЮKassa `200`, чтобы уведомление не повторялось.
Ровно одно письмо на платёж — гейт через `payments.status='orphaned'`
([`server.js:428`](../server.js:428): повторный вебхук по тому же платежу выходит на этой
проверке раньше повторной попытки применения).

### 2.4. `GET /api/payments/:id`

[`server.js:492`](../server.js:492). Только свой платёж (`getPaymentById(userId, id)` — чужой/
несуществующий → `404`). Если строка ещё `pending` и есть `yookassa_id` — опрашивает ЮKassa сама
и применяет тем же `applySucceededPayment`, на случай запаздывающего вебхука.

### 2.5. Письмо владельцу об оплате

[`sendPaymentOwnerEmail`](../server.js:319) — только на первое применение (`result.applied ===
true`), тема с `[ТЕСТ]`, если `ykPayment.test === true` (не по своей переменной окружения —
меньше риска забыть снять признак при переключении на боевой магазин). Все пользовательские
значения — через `escapeHtml`.

### 2.6. Отмена подписки пользователем

`POST /api/subscription/cancel` удалён. `cancelSubscription()` в `db.js` **не удалена** —
grep (`cancelSubscription` в `server.js`) показал второе место использования: отзыв подписки в
админке (`DELETE /api/admin/users/:id/subscription`), который часть 2.6 явно не трогает.

### Как проверено без реальных ключей

- `node --check` для `server.js`, `server/yookassa.js`, `server/db.js` — на каждом коммите.
- Заглушка `fetch` (без сети): подтверждена точная форма запроса создания платежа (`amount.value`
  строкой с копейками, `capture:true`, `confirmation.return_url`, `metadata`), заголовок
  `Idempotence-Key`, Basic-авторизация, разбор `getPayment`/`getRefund`, что 401 не логирует
  секрет/заголовки, и что `getPayment('../../evil')` / id с пробелом бросают
  `yookassa_invalid_id` до похода в сеть, а валидный uuid корректно кодируется в URL.
- Ветвление вебхука и `GET /api/payments/:id` (succeeded/mismatch/orphaned/canceled, полный/
  частичный возврат, неизвестное событие) — разбором кода вручную. Без реальной БД

  транзакционные ветки `applySucceededPayment`/`applyRefund` через настоящий Postgres нельзя.

## Исправление после части 2: любой возврат закрывает доступ

По п. 6.1 оферты возврат при отказе от Клуба **всегда частичный** (сумма за использованные дни
удерживается) — значит правило части 2.3 «частичный возврат — доступ не меняем» было ошибкой
ТЗ: под него подпадал бы весь поток возвратов Клуба, и доступ никогда бы не закрывался по
возврату. Исправлено: [`server.js:463`](../server.js:463) зовёт `applyRefund` для любого
успешного возврата, полного или частичного; идемпотентность — через `result.alreadyRefunded` от
`applyRefund` (повторный возврат по тому же платежу не переприменяется, письмо не дублируется).
Письмо владельцу при частичном возврате оставлено, текст изменён на «доступ по этой оплате
закрыт» ([`sendPartialRefundEmail`](../server.js:365): сумма платежа, сумма возврата, id
ЮKassa, время по Москве).
